# 无锁编程
---
## 0. 学习边界

- **类别**：**B 类（常用工具）**
- **判断理由**：锁竞争是并发程序的头号性能杀手；无锁编程（原子操作、CAS、内存序）是高并发中间件的标配技术，也是理解 [[缓存一致性]] 协议价值的直接应用场景。
---
## 1. 这个知识点解决什么问题？

> **我们遇到了什么麻烦**：
> 用锁保护共享数据时，竞争激烈会导致线程挂起、上下文切换、缓存行反复失效（[[伪共享]] 加剧）、甚至优先级反转。锁的代价随核心数增长放大。
> 因此引入 **无锁编程**：用硬件原子操作（RMW）完成"检查-修改"，用 CAS 循环实现乐观更新，配合内存序（acquire/release）保证可见性——没有阻塞，靠"失败重试"而非"等待"。
---
## 2. 为什么它重要？它有什么用？

- **连接大图景**：无锁编程是 [[缓存一致性]] 协议的软件收益面（原子指令走一致性协议）；与 [[锁优化]] 构成"同步开销"的两条路线。
- **实际应用场景**：Linux 内核（RCU、seqlock）、Java Concurrent 包、Kafka/Redis 等中间件、游戏服务器。
- **高频题型/任务**：CAS 实现原子计数器；ABA 问题分析；acquire/release 语义；无锁栈/队列手写。
---
## 3. 学它之前需要哪些前置知识？

1. **[[缓存一致性]]**：原子操作如何通过 MESI 协议在硬件上实现"独占-修改"。
2. **[[锁优化]]**：锁的代价具体在哪——无锁要解决的痛点清单。
3. **[[伪共享]]**：无锁结构的缓存行布局同样会踩伪共享的坑。
---
## 4. 用直觉语言解释它

> «"锁像厕所门闩：进去先锁门，别人只能等（阻塞）；无锁像抢答器：谁先按下（原子操作）谁赢，没抢到的不是干等而是立刻再试（CAS 循环）。内存序像对讲机规则：release 是'我先说完你再说'，acquire 是'听完之前我不动'——只约束顺序，不锁门。"»

- **直觉类比/几何图像**：CAS=乐观并发（先试后验）；内存序=顺序契约而非互斥。
- **为什么很自然**：竞争激烈时"重试"比"等待"便宜；把互斥降级为顺序约束，是"按需最少同步"。
- **一句话直觉本质**：**用原子 RMW 指令代替锁，用 CAS 重试代替阻塞，用内存序保证可见性——把同步开销从内核级降到指令级。**
---
## 5. 正式定义、核心公式、符号解释

### 1. 最核心定义
- **原子操作（RMW）**：读-改-写一气呵成的硬件指令（`xchg`、`lock cmpxchg`、`atomic_fetch_add`）。
- **CAS**：`if (*p == expected) *p = desired; return 是否成功`——乐观更新原语。
- **内存序**：`relaxed`（只保证原子）、`acquire`（其后读写不越过）、`release`（其前读写不越过）、`seq_cst`（全序）。
- **ABA 问题**：CAS 期间值从 A 变 B 又变回 A，CAS 误判"未被修改"。

### 2. 核心公式（CAS 循环）
$$\text{do } \{ old = load(p);\ new = f(old); \} \text{ while } (!\text{CAS}(p, old, new))$$

### 3. 符号说明表

| 符号 | 含义 | 取值范围 / 量纲 | 备注 |
| :--- | :--- | :--- | :--- |
| $p$ | 共享内存地址 | 对齐 8 字节 | 原子操作要求对齐 |
| $old$ | 预期旧值 | 任意 | CAS 比较依据 |
| $new$ | 期望新值 | 任意 | 由 old 派生 |
| acquire/release | 顺序约束 | 单向 | 配对使用 |

### 4. 常见变体与适用条件
- **适用条件**：单写多读、高频更新热点、不允许阻塞的实时/内核场景。
- **限制条件**：写者激烈竞争时 CAS 重试风暴（活锁）；正确性极难论证；ABA 与内存序错误难调试；并非所有结构都可无锁化。
---
## 6. 推导思路和思想来源

- **最初困难**：锁在低竞争下开销小，高竞争下成瓶颈（阻塞+切换+缓存震荡）。
- **直接方法局限**：锁的"等待"要求内核调度参与；缩小临界区只能缓解。
- **关键"转念"**：同步的本质是"对共享位置的原子修改"——硬件 RMW 指令天然原子；"失败"不再等待而是**重试**（乐观并发）；可见性用内存序精确控制而非全量屏障。
- **推导主线与动机**：锁开销∝等待 → 消除等待=失败立即重试 → 重试正确性靠 CAS → 多步修改需无锁结构（Treiber 栈、MS 队列）→ 回收问题引出 ABA 与 Hazard Pointer。
- **为什么自然得到此结论**：数据库"乐观锁"（版本号验证）思想下沉到指令级，就是 CAS。
---
## 7. 例子：基础 → 中等 → 实际应用

### 例子 1：基础例子（可手算）
- **题目**：用 CAS 实现原子递增 `atomic_inc(&x)`。
- **解题思路与最终答案**：循环：读 `old=x`；`new=old+1`；CAS 失败说明别人改了，重读重试。C11 一行：`atomic_fetch_add(&x, 1)`。
- **易错点**：忘记 CAS 循环（单次 CAS 不保证成功）。
- **🤔 追问**：两线程各递增 100 万次，最终值？——200 万；CAS 循环保证无丢失更新。

### 例子 2：中等例子（条件判断与多步推理）
- **题目**：Treiber 无锁栈 push 为什么必须用 CAS 循环而非直接赋值？
- **解题思路与完整解答**：`push(x)`：读 top；`x->next = top`；`CAS(&top, top, x)`——若中间有别的线程改动 top，CAS 失败重试。**关键推理**："检查-链接"被压缩进一条指令，保证链接基于最新 top。
- **易错点**：把顺序写成先 CAS 再链接 next（链断裂）。

### 例子 3：实际应用例子（真实场景/代码）
- **实际价值与转化**：Java `ConcurrentLinkedQueue`（MS 队列）与 `AtomicLong` 是标准无锁实现；Redis `INCR` 是服务端原子计数；Linux RCU 让读路径零开销。
```c
atomic_int count = ATOMIC_VAR_INIT(0);
int old = atomic_load_explicit(&count, memory_order_relaxed);
while (!atomic_compare_exchange_weak(&count, &old, old + 1))
    ;  // 失败时 old 已更新为最新值，直接重试
```

## 8. 常见误区和易混概念

### 误区 1：以为"无锁 = 无等待、永远更快"
- **错误直觉与原因**：无锁没有阻塞一定更快——高写竞争下 CAS 重试风暴可能比锁更糟（活锁）。
- **正确理解**：无锁在"竞争中等、操作极短"时胜出；高竞争时锁（带排队/退避）可能更稳。

### 误区 2：以为"原子操作 = 完全同步"
- **错误直觉与原因**：用了原子就不用关心顺序——`relaxed` 只保证单点原子，不保证跨线程可见性。
- **正确理解**：原子性与内存序是两个维度，缺一不可。

### 概念对比表

| 概念 | 核心问题 | 关键区别 | 典型使用场景 |
| :--- | :--- | :--- | :--- |
| 互斥锁 | 互斥+等待 | 阻塞、内核参与 | 临界区较长 |
| 自旋锁 | 互斥+忙等 | 不切换、占 CPU | 临界区极短 |
| CAS/原子 | 原子修改 | 无等待、可重试 | 计数器、无锁结构 |
| RCU | 读无锁写替换 | 读零开销、延迟回收 | 内核读多写少 |

### 题目与解析
#### 1. 原子操作与内存序的区别是什么？
> [!question]- 答案解析
> - **答案**：原子性保证"读-改-写"不可分割；内存序保证跨线程可见性顺序。`relaxed` 只有前者。
> - **解析**：relaxed 递增计数器值正确，但用它发布指针可能让读者看到未初始化数据。
#### 2. 用 CAS 循环实现"把 x 翻倍"的原子操作。
> [!question]- 答案解析
> - **答案**：`old = load(&x); do { new = old*2; } while (!CAS(&x, &old, new));`（失败时 old 自动刷新）。
> - **解析**：CAS 失败意味着期间有人修改，重读最新值再算。
#### 3. 什么场景下无锁编程不划算？
> [!question]- 答案解析
> - **答案**：临界区较长、写竞争极其激烈（重试风暴）、正确性难以验证的复杂结构。
> - **解析**：无锁擅长"操作极短、竞争中等"；长临界区用锁更优。
#### 4. 说明 ABA 问题：线程 A 读 top=X 后休眠，B pop 掉 X 再 push 回 X，A 醒来 CAS 为何误判？
> [!question]- 答案解析
> - **答案**：CAS 只比较值（地址 X 相同），A 误判无人修改，但 X 的 next 已被 B 改变，栈结构被破坏。解法：版本号/标记指针比较 (地址,版本)，或 Hazard Pointer/RCU 延迟回收。
> - **解析**：ABA 本质是"值比较无法区分没变与变了一圈又回来"。
#### 5. 简述 Michael-Scott 无锁队列的基本思路与难点。
> [!question]- 答案解析
> - **答案**：哨兵节点+头尾指针；入队 CAS 尾的 next，出队 CAS 头。难点：尾指针滞后（辅助推进）、节点回收（ABA/Hazard Pointer）、内存序配对。
> - **解析**：队列比栈难在"两端的 next 都要 CAS 且互相依赖"。
