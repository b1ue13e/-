# 文件系统
---
## 0. 学习边界

- **类别**：**B 类（常用工具）**
- **判断理由**：文件系统是"数据持久化"的标准答案与块设备 IO（[[DMA机制]]）之上的核心抽象；理解 inode/块分配/日志对系统编程、数据库内核与面试直接有用。
---
## 1. 这个知识点解决什么问题？

> **我们遇到了什么麻烦**：
> 磁盘是"一堆可寻址扇区"，但程序员要的是"命名、可增长、可随机读写的文件"与"有层级的目录"。直接操作扇区危险且无法组织；断电还会让正在写的文件系统处于不一致状态。
> 因此引入 **文件系统**：inode 记录文件元数据与数据块位置，目录树把文件名映射到 inode，分配策略管理空闲块，**日志**保证崩溃后恢复到一致状态。
---
## 2. 为什么它重要？它有什么用？

- **连接大图景**：文件系统是 [[DMA机制]]/磁盘 IO 之上的第一层软件抽象，与 [[虚拟内存]]（page cache）、[[分页机制]]（mmap）深度耦合。
- **实际应用场景**：Linux 磁盘管理（EXT4/XFS/Btrfs）、数据库 WAL 与页缓存、嵌入式 Flash 文件系统。
- **高频题型/任务**：inode 最大文件大小计算；软/硬链接区别；分配方式对比；日志如何保证崩溃一致性。
---
## 3. 学它之前需要哪些前置知识？

1. **[[DMA机制]]**：数据如何从磁盘到内存——文件读写的物理承载。
2. **[[虚拟内存]]**：page cache 与 mmap 让文件读写走内存路径。
3. **[[进程调度]]**：IO 阻塞/唤醒的进程视角。
---
## 4. 用直觉语言解释它

> «"文件系统像图书馆藏书管理：inode 是'索书卡'（书名+书架位置）；目录是'分类索引'（书名→索书卡）；空闲块管理是'空书架登记簿'；日志是'借阅流水账'——先把'要改什么'写在账本上再动手，断电后对着账本重放或撤销，保证书架不会停在'改了一半'的状态。"»

- **直觉类比/几何图像**：inode=元数据卡；目录=名字→卡片映射；日志=先记账后操作（WAL）。
- **为什么很自然**：把"数据"与"描述数据的元数据"分离是任何索引系统的通用结构；先写意图再执行是原子性的经典手法。
- **一句话直觉本质**：**文件系统 = inode（元数据）+ 目录树（命名）+ 分配策略（空间管理）+ 日志（崩溃一致性）。**
---
## 5. 正式定义、核心公式、符号解释

### 1. 最核心定义
- **文件系统**：在块设备之上组织、命名、存储与保护数据的软件层。
- **inode**：文件元数据：大小、权限、时间戳、块指针（直接/间接/双重间接）。
- **目录**：文件名 → inode 号的映射表。
- **日志（Journal）**：先写操作意图（WAL）再改主数据结构；崩溃后重放/回滚。

### 2. 核心公式（inode 最大文件大小）
$$S_{\max} = D\cdot B + \frac{B}{P}\cdot B + \left(\frac{B}{P}\right)^2\cdot B + \left(\frac{B}{P}\right)^3\cdot B$$

- $D$ 直接块、单/双/三间接块各若干，$B$ 块大小，$P$ 块指针大小。

### 3. 符号说明表

| 符号 | 含义 | 取值范围 / 量纲 | 备注 |
| :--- | :--- | :--- | :--- |
| $B$ | 块大小 | 4KB（EXT4 默认） | 分配粒度 |
| $P$ | 块指针大小 | 4~8 字节 | 决定每块指针数 |
| $D$ | 直接块指针数 | 如 12 | 小文件免间接寻址 |
| 日志 | 事务记录 | 顺序写区 | WAL 思想 |

### 4. 常见变体与适用条件
- **变体**：EXT4（日志+块组）、XFS（B+树）、Btrfs（COW+快照）、FAT/NTFS、F2FS（Flash）。
- **适用条件**：机械盘选日志+块组；SSD/Flash 选 COW 或 F2FS。
- **限制条件**：日志有双写开销（ordered 模式只记元数据）；inode 表占空间；目录项多需 B+树/htree。
---
## 6. 推导思路和思想来源

- **最初困难**：直接管理扇区无法表达"文件"；断电把半写状态留在盘上。
- **直接方法局限**：连续分配碎片严重且文件无法增长；全盘 fsck 恢复太慢。
- **关键"转念"**：① 索引分配——inode 集中元数据，数据块任意分散（间接块支持大文件）；② 日志——借鉴数据库 WAL，**先记意图后执行**，恢复时间从 O(全盘) 降到 O(日志)。
- **推导主线与动机**：文件增长 → 链式/索引分配 → 索引 O(1) 定位 → 大文件多级间接 → 崩溃一致性 → 日志事务 → 按需重放。
- **为什么自然得到此结论**：与页表（稀疏索引）同构：数据分散、索引集中、按需分配。

## 7. 例子：基础 → 中等 → 实际应用

### 例子 1：基础例子（可手算）
- **题目**：块 4KB、指针 4 字节、直接块 12、单/双/三间接各 1。最大文件多大？
- **解题思路与最终答案**：每块指针 $=4096/4=1024$：直接 $12\times4K=48K$；单间接 $4MB$；双间接 $4GB$；三间接 $4TB$。合计 ≈ 4.004 TB。
- **易错点**：忘记乘块大小。
- **🤔 追问**：指针改 8 字节？——每块 512 指针，容量减半但可寻址更大磁盘：元数据开销 vs 容量的权衡。

### 例子 2：中等例子（条件判断与多步推理）
- **题目**：硬链接与软链接有什么区别？`ln a b` 与 `ln -s a c` 各做了什么？
- **解题思路与完整解答**：硬链接：b 与 a 共享同一 inode（链接计数+1），删一个不影响另一个，不能跨文件系统；软链接：c 是存"a 路径字符串"的特殊文件，a 删除后 c 悬空。**关键推理**：硬链接在 inode 层共享，软链接在路径层引用——`mv a` 让软链接失效而硬链接不受影响。
- **易错点**：认为软链接"复制"了文件。

### 例子 3：实际应用例子（真实场景/代码）
- **实际价值与转化**：数据库的数据文件 + WAL 日志文件——崩溃恢复重放 WAL，是文件系统日志思想的软件层复用；`mmap` 大文件让 page cache 管理 IO（page fault 驱动按需读入）。
```bash
stat file          # inode 元数据（含链接数）
ln -s src dst      # 软链接
df -i /            # inode 使用率（inode 耗尽也会"磁盘满"）
mount -o data=ordered /dev/sda1 /mnt   # EXT4 日志模式
```

## 8. 常见误区和易混概念

### 误区 1：以为"文件内容必须连续存放"
- **错误直觉与原因**：文件是连续字节流，磁盘上也应连续——连续分配无法增长且碎片严重。
- **正确理解**："连续"是抽象承诺，物理分散由 inode 索引保证。

### 误区 2：混淆"日志（journal）"与"日志文件（log file）"
- **错误直觉与原因**：都是"日志"——journal 是崩溃一致性机制（WAL 重放用），log file 是应用输出记录。
- **正确理解**：journal 是"意图账本"，log 是"事件流水"。

### 概念对比表

| 概念 | 核心问题 | 关键区别 | 典型使用场景 |
| :--- | :--- | :--- | :--- |
| 连续分配 | 空间连续 | 碎片多、难增长 | 早期 FS、ISO9660 |
| 链式分配 | 块链连接 | 随机访问 O(n) | FAT |
| 索引分配 | inode 集中索引 | 随机访问 O(1) | EXT4、XFS |
| 日志 vs 快照 | 一致性手段 | 重放 vs COW 副本 | EXT4 journal、Btrfs |

| 题号 | 类型 | 难度 | 考查点 |
| :--- | :--- | :--- | :--- |
| 1 | 概念辨析 | 基础 | inode vs 目录项 |

| 4 | 变式/综合 | 中等 | 崩溃一致性 |

### 题目与解析
#### 1. 目录项（dentry）与 inode 的关系是什么？
> [!question]- 答案解析
> - **答案**：目录项是"文件名→inode 号"映射，多个目录项可指向同一 inode（硬链接）；inode 存真正的元数据与块指针。
> - **解析**：unlink 只减链接计数，为 0 才真正释放。
#### 2. 块 1KB、指针 4 字节、直接块 10、单间接 1。最大文件多大？
> [!question]- 答案解析
> - **答案**：$10\times1K + (1024/4)\times1K = 10K + 256K = 266$ KB。
> - **解析**：每块可存 256 个指针。
#### 3. 硬链接能否跨文件系统？软链接目标被删除后发生什么？
> [!question]- 答案解析
> - **答案**：硬链接不能跨文件系统（inode 号只在同一 FS 内有效）；软链接目标删除后成悬空链接，访问报 No such file。
> - **解析**：硬链接共享 inode，软链接是路径字符串。
#### 4. 断电发生在"日志已 commit、数据未写完"时，恢复流程如何保证一致？
> [!question]- 答案解析
> - **答案**：日志 commit 即意图已持久化；恢复时重放（redo）已提交事务，丢弃未提交事务（undo），主结构回到事务边界。
> - **解析**：WAL 核心是"日志先于数据落盘"；ordered 模式只记元数据日志。
#### 5. 设计一个支持"文件可增长、随机访问 O(1)"的最简文件系统，画出关键结构。
> [!question]- 答案解析
> - **答案**：磁盘分超级块、inode 表（12 直接+单/双间接指针）、数据区、空闲位图。创建=分配 inode+目录项；读偏移=块号定位；写超范围=分配新块更新指针。
> - **解析**：即 EXT2/3 骨架；增长由间接块支持，随机访问由索引保证。
