# 进程调度
---
## 0. 学习边界

- **类别**：**A 类（核心概念，必须深挖）**
- **判断理由**：调度器是操作系统的"大脑"——决定 CPU 时间分配，直接决定响应性、吞吐与公平性；是 OS 课程、面试与 [[项目-调度器模拟]] 的核心主题。
---
## 1. 这个知识点解决什么问题？

> **我们遇到了什么麻烦**：
> 系统同时有几十上百个进程，CPU 核心只有几个。谁先跑？跑多久？FCFS 让一个长任务卡死所有交互程序；轮流 1ms 又切换开销过大；且切换本身很贵（保存/恢复寄存器、刷新 TLB、换页表）。
> 因此引入 **进程调度**：调度器在"何时切换、切换到谁、运行多久"上决策，在**吞吐、响应、公平、开销**间权衡；时钟中断是它的"闹钟"，上下文切换是它的代价。
---
## 2. 为什么它重要？它有什么用？

- **连接大图景**：调度是进程生命周期的驱动轮；与 [[中断机制]]（调度时机）、[[分页机制]]（换页表/TLB）、[[DMA机制]]（IO 唤醒）环环相扣。
- **实际应用场景**：Linux CFS 调优（nice、cgroup cpu 份额）、实时系统、容器 CPU 限额。
- **高频题型/任务**：甘特图计算平均等待/周转；策略对比；调度时机分析；上下文切换开销计算。
---
## 3. 学它之前需要哪些前置知识？

1. **[[中断机制]]**：时钟中断触发调度决策——抢占式调度的硬件基础。
2. **[[分页机制]]**：上下文切换涉及页表（CR3）与 TLB 刷新，成本从何而来。
3. **[[虚拟内存]]**：进程地址空间隔离——切换必须换页表。
---
## 4. 用直觉语言解释它

> «"调度器像医院分诊台：FCFS 是'先来先挂号'（公平但重病号堵死一切）；SJF 是'先治轻症'（平均等待最短但重症可能饿死）；RR 是'每人看 5 分钟轮转'（响应快但切换频繁）；MLFQ 是'分层分诊'——新来的进急诊（高优先级），看久了降级到普通门诊，既保响应又保吞吐；Linux CFS 按'虚拟时间记账'：谁欠的时间多谁先跑。"»

- **直觉类比/几何图像**：调度=排队论；时间片=轮转；vruntime=公平账本。
- **为什么很自然**：目标互相冲突（响应 vs 吞吐），单一策略必有缺陷，分层+记账是工程折中的必然。
- **一句话直觉本质**：**调度 = 在切换时机（何时）、选择策略（选谁）、时间尺度（多久）三个旋钮上做多目标权衡的排队管理。**
---
## 5. 正式定义、核心公式、符号解释

### 1. 最核心定义
- **调度器**：从就绪队列选择下一个运行进程的内核组件。
- **调度策略**：FCFS、SJF/SRTF、RR、优先级、MLFQ、CFS。
- **上下文切换**：保存当前进程 CPU 状态（寄存器、PC、栈指针、页表基址），恢复下一个进程状态。
- **抢占**：时钟中断强制剥夺当前进程 CPU（时间片耗尽）。

### 2. 核心公式（平均等待与切换开销）
$$T_{\text{avg wait}} = \frac{1}{n}\sum_{i=1}^{n}(T_{\text{start},i} - T_{\text{arrive},i}),\qquad \text{切换占比} = \frac{n \cdot t_{\text{switch}}}{T_{\text{total}}}$$

### 3. 符号说明表

| 符号 | 含义 | 取值范围 / 量纲 | 备注 |
| :--- | :--- | :--- | :--- |
| $T_{\text{start}}$ | 进程首次运行时刻 | 时间戳 | 等待=start-arrive |
| $T_{\text{arrive}}$ | 进程到达时刻 | 时间戳 | 就绪队列入场 |
| $t_{\text{switch}}$ | 单次切换开销 | 1~10μs | 含 TLB 刷新 |
| 时间片 | RR 轮转量子 | 1~100ms | 现代 OS 1-4ms |

### 4. 常见变体与适用条件
- **变体**：FCFS（批处理）、SJF（理论最优）、RR（交互）、MLFQ（通用折中）、CFS（Linux 默认）、实时 RM/EDF。
- **适用条件**：交互负载选短时间片/高优先级；批处理选 SJF 类；实时选 RM/EDF。
- **限制条件**：SJF 需预知时长（用历史预测）；优先级策略有饥饿风险（需老化）；实时需可抢占内核与优先级反转处理。
---
## 6. 推导思路和思想来源

- **最初困难**：多进程共享 CPU，FCFS 导致长任务饿死交互任务。
- **直接方法局限**：FCFS 平均等待差；SJF 最优但需未来信息且长任务可能饿死。
- **关键"转念"**：① RR——"轮流跑一段"，交互任务最多等一个时间片；② MLFQ——多级队列+动态升降级同时满足响应与吞吐；③ CFS——放弃优先级队列，用 vruntime 账本做完全公平调度（红黑树取最小者）。
- **推导主线与动机**：等待最小化 → SJF（不可行）→ 时间片轮转逼近 → 响应与吞吐冲突 → MLFQ 折中 → 公平性形式化 → CFS 记账。
- **为什么自然得到此结论**：资源分配都可归结为"队列+优先级+公平性"权衡——排队理论的 OS 实例。

## 7. 例子：基础 → 中等 → 实际应用

### 例子 1：基础例子（可手算）
- **题目**：A/B/C 同时到达，运行 24/3/3。FCFS 与 SJF 平均等待？
- **解题思路与最终答案**：FCFS（A→B→C）：等待 0,24,27，平均 17；SJF（B→C→A）：0,3,6，平均 3。
- **易错点**：SJF 按运行时长排序；平均等待≠平均周转。
- **🤔 追问**：若 A 先到 1 秒、B/C 后到？——非抢占 SJF 仍先跑 A 24 秒，交互任务卡死；这就是需要抢占（SRTF）与 RR/MLFQ 的理由。

### 例子 2：中等例子（条件判断与多步推理）
- **题目**：时间片从 10ms 减到 1ms，切换 0.1ms。对响应与利用率的影响？
- **解题思路与完整解答**：响应上限从 10ms×n 降到 1ms×n（更好）；切换占比从 1% 升到 10%（利用率降）。**关键推理**：时间片不能小于切换开销的合理倍数——现代 OS 用 1-4ms 且切换 <1μs，占比可控。
- **易错点**：只算响应改善，漏算切换占比。

### 例子 3：实际应用例子（真实场景/代码）
- **实际价值与转化**：Linux CFS：vruntime = 实际运行时间÷权重，红黑树取最小者运行；`nice` 调整权重；cgroup `cpu.shares` 按比例分 CPU；`sched_setaffinity` 绑核减少缓存/TLB 抖动。
```bash
nice -n -10 ./heavy        # 提高权重
taskset -c 2,3 ./app       # CPU 亲和性
cat /proc/<pid>/sched      # vruntime 与调度统计
```

## 8. 常见误区和易混概念

### 误区 1：以为"SJF 永远最好"
- **错误直觉与原因**：平均等待最短就该用它——需预知时长，长任务可能无限期饿死。
- **正确理解**：SJF 是理论基准，实际用 MLFQ/CFS 折中。

### 误区 2：混淆"调度"与"上下文切换"
- **错误直觉与原因**：调度=切换一回事——调度是**决策**（选谁），切换是**执行**（保存/恢复）。
- **正确理解**：调度器决策，可能决定不切换（继续当前进程）。

### 概念对比表

| 策略 | 核心目标 | 关键特征 | 典型场景 |
| :--- | :--- | :--- | :--- |
| FCFS | 公平 | 无抢占、长任务阻塞 | 批处理 |
| SJF/SRTF | 最短等待 | 需预知时长 | 理论基准 |
| RR | 响应 | 时间片轮转 | 分时系统 |
| MLFQ | 响应+吞吐 | 多级队列动态升降 | 通用 OS |
| CFS | 公平+低延迟 | vruntime 记账 | Linux 默认 |

### 题目与解析
#### 1. 抢占式与非抢占式调度的本质区别？
> [!question]- 答案解析
> - **答案**：抢占式允许时钟中断在时间片耗尽时强制剥夺；非抢占式只允许进程主动让出（阻塞/退出）。
> - **解析**：抢占依赖时钟中断；非抢占实现简单但交互性差。
#### 2. 三个进程同时到达，运行 5/2/8。SJF 平均等待？
> [!question]- 答案解析
> - **答案**：顺序 2→5→8，等待 0,2,7，平均 3。
> - **解析**：同时到达时 SJF 即最短运行时间优先。
#### 3. 时间片过小和过大的危害各是什么？
> [!question]- 答案解析
> - **答案**：过小→切换开销占比上升、利用率下降；过大→交互响应变差（近似 FCFS）。
> - **解析**：合理值≈切换开销的千倍量级（如 1ms vs 1μs）。
#### 4. MLFQ 中一个 CPU 密集进程反复用满时间片，会发生什么？
> [!question]- 答案解析
> - **答案**：用完高优先级时间片后降级（量子更长），一路降到最低队列——交互进程保持高优先级，CPU 密集进程被"惩罚"。
> - **解析**：升降级动态识别进程类型；配合老化防止饥饿。
#### 5. 论证 CFS 用 vruntime 记账为何同时近似公平与低延迟。
> [!question]- 答案解析
> - **答案**：vruntime=实际运行时间÷权重，红黑树取最小者运行→权重相同则运行时间趋于相等（公平）；新唤醒进程 vruntime 置最小→立即获 CPU（低延迟）；IO 密集进程运行少、vruntime 小→天然优待。
> - **解析**：公平由账本保证而非轮转表；无需复杂优先级即可自组织。
