# VM栈机与函数调用

---

## 0. 学习边界

- **类别**：**A 类（核心概念，必须深挖）**
- **判断理由**：HW07-08（Project 07-08）是工具链的第二段，VM 语言是"高级语言与硬件之间"的稳定中间层：编译器前端只需生成 VM 代码，翻译成汇编的脏活全在 VM Translator。栈机模型、内存段映射、调用约定三样东西在 HW09-11（Jack 编译器）中全部复用；函数调用约定更是真实 ABI（x86/ARM 调用约定）的微型原型。

---

## 1. 这个知识点解决什么问题？

> **我们遇到了什么麻烦**：直接写 Hack 汇编做复杂程序太痛苦——没有表达式嵌套、没有局部变量作用域、没有函数，一个 `x = (a+b)*(c-d)` 就要手工管理一堆临时寄存器。若高级语言编译器直接生成汇编，换一个目标平台就要重写整个后端。因此必须引入**中间层**：一门平台无关的**VM 语言**（栈机指令集）。编译器前端生成 VM 代码，**VM Translator** 把 VM 代码翻译成 Hack 汇编。新麻烦随之而来：如何用"栈"表达算术/比较/跳转？函数调用时现场（返回地址、局部环境）怎么保存恢复？这就是本页的栈机模型与调用约定。

---

## 2. 为什么它重要？它有什么用？

- **连接大图景**：HW07 打通"表达式与流程控制"，HW08 打通"函数与递归"，两段合起来就是完整的可编程抽象；HW09-11 的 Jack 编译器只产 VM 代码（前端），后端翻译全部复用本层。它是 Nand2Tetris 全链路中"分层解耦"的典范。
- **实际应用场景**：JVM（Java 字节码）、Python bytecode、LLVM IR、WebAssembly 都是"中间表示 + 后端翻译"思想的直接后代；函数调用约定（帧、返回地址、恢复现场）是所有真实 ABI 的共同骨架。
- **高频题型/任务**：push/pop 的段寻址翻译（8 种段）；算术/比较指令的汇编模板；`call`/`function`/`return` 的帧操作（FRAME、RET、恢复现场顺序）；递归程序（如 factorial）的栈帧跟踪。

## 4. 用直觉语言解释它

> «"VM 语言像一张'快递单'，只写'从哪个仓库取什么货、做什么加工'，不关心仓库内部布局；VM Translator 是'仓库分拣员'，把每张快递单翻译成仓库自己的搬运指令（Hack 汇编）。函数调用则像办公室里的'临时离岗'：你要去别的工位干活（被调函数），就把手头进度（帧：返回地址+现场）锁进档案柜（栈），干完回来按档案恢复进度。"»

- **直觉类比/几何图像**：栈 = 自助餐取餐台（后进先出）：表达式求值把中间结果逐盘叠上去，用完就取走；函数调用 = 档案柜里的"一摞档案"，最上面是当前正在干的活，干完撕掉最上面一张，露出上一份。
- **为什么很自然**：因为"嵌套"天然是后进先出——最内层表达式先算完、最内层调用先返回；栈正好用一套机制统一了表达式求值与函数调用。
- **一句话直觉本质**：**把"所有计算都先压栈、再从栈顶取"作为唯一规则，表达式、比较、跳转、函数调用就都变成栈上的机械动作；调用约定只是'把现场打包压栈、返回时原样恢复'的固定流程。**

---

## 5. 正式定义、核心公式、符号解释

### 1. 最核心定义
- **VM 语言**：面向栈的中间语言；两类命令：栈操作（`push seg i` / `pop seg i`）与流程操作（算术/比较/`label`/`goto`/`if-goto`/`function`/`call`/`return`）。
- **VM Translator**：把每个 `.vm` 文件翻译成等价的 `.asm`（Hack 汇编），本身是"编译器"（1 条 VM 指令 → 多条汇编）；**函数调用约定**即 `call f n`、`function f m`、`return` 三条指令共同实现的"现场保存→转移控制→恢复现场"协议。

### 2. 核心公式
算术二元操作（先弹 y 再弹 x，结果 = x op y）：
$$\text{add}: \ \texttt{@SP}\ \texttt{AM=M-1}\ \texttt{D=M}\ \texttt{A=A-1}\ \texttt{M=D+M}\qquad (x{+}y \to \text{栈顶})$$

段寻址统一形式：
$$\text{push}\ \text{seg}\ i:\ \text{addr} = \text{base}(\text{seg}) + i;\quad \text{stack}[\texttt{SP}] = \text{RAM}[\text{addr}];\ \texttt{SP++}$$
$$\text{base}: \text{arg}{=}\texttt{ARG},\ \text{local}{=}\texttt{LCL},\ \text{this}{=}\texttt{THIS},\ \text{that}{=}\texttt{THAT},\ \text{temp}{=}5,\ \text{static}{=}16,\ \text{pointer}{=}\texttt{THIS}$$

函数调用（`call f nArgs` 执行后）：
$$\texttt{ARG} = \texttt{SP} - 5 - nArgs,\qquad \texttt{LCL} = \texttt{SP},\qquad \text{SP} \to \text{函数 } f \text{ 体}$$

返回（`return`）：
$$\texttt{RET} = \text{RAM}[\texttt{LCL}-5];\quad \text{RAM}[\texttt{ARG}] = \text{pop}();\quad \texttt{SP} = \texttt{ARG}+1;\quad \text{恢复 THAT/THIS/ARG/LCL};\quad \text{goto RET}$$

### 3. 符号说明表

| 符号 | 含义 | 取值范围 | 备注 |
| :--- | :--- | :--- | :--- |
| `SP` | 栈指针（RAM[0]） | 指向栈顶上空位 | 压栈先写后 ++ |
| `LCL/ARG` | 局部/实参段基址 | RAM[1]/RAM[2] | 每函数一帧 |
| `THIS/THAT` | this/that 段基址 | RAM[3]/RAM[4] | 指向堆对象/数组 |
| `seg i` | 段偏移寻址 | $i\ge 0$ | constant 仅 push |
| `nArgs/nVars` | 实参/局部变量个数 | $\ge 0$ | call/function 参数 |

### 4. 常见变体与适用条件
- **变体**：比较指令（`eq/lt/gt`）无 Hack 直译，需"减法 + 跳转标签对 + 结果回填 0/-1"；标签必须带唯一编号（`EQ_1`、`END_1`）避免多文件冲突。
- **适用条件**：VM 面向"单线程顺序执行"；HW07 无函数（单文件），HW08 引入函数（多文件、`Sys.init` 为入口）。
- **限制条件**：`pointer 0/1` 与 `temp 0..7` 范围固定；递归深度受 RAM 上限约束（每帧约 nVars+5 个字）。

## 6. 推导思路和思想来源

- **最初困难**：高级语言的结构（表达式嵌套、局部变量、函数调用）与平坦的 Hack 汇编之间鸿沟太大，直接翻译需要为每种结构写专门模板，组合爆炸且无法复用；寄存器机汇编里"临时值放哪"是程序员的心智负担，每次调用都要手工约定"谁保存返回地址"，程序一复杂就乱。
- **关键"转念"**：引入**操作数栈**统一表达式的临时值（谁算完就压栈，需要就用栈顶）；引入**运行时栈帧**统一函数的局部环境（调用 = 压一帧，返回 = 弹一帧）。后进先出恰好匹配嵌套求值与嵌套调用。
- **推导主线与动机**：push/pop 原语 → 算术/比较翻译 → 8 个内存段的基址映射（把"变量"翻译成"段偏移"）→ call 压返回地址与旧帧指针、重设 ARG/LCL → return 用 FRAME 逆序恢复。每一层都在"把复杂语义降为栈上的机械动作"。
- **为什么自然得到此结论**：因为"嵌套"与"后进先出"是同一结构的两面；栈是唯一同时服务表达式与调用的数据结构，这是计算机科学里"一个机制两用"的经典案例。

## 7. 例子：基础 → 中等 → 实际应用

### 例子 1：基础例子（可手算）
- **题目**：跟踪 `push constant 2`、`push constant 3`、`add` 的栈演变，并翻译 `add` 为 Hack 汇编。
- **解题思路与关键步骤**：`push constant 2`：`@2; D=A; @SP; A=M; M=D; @SP; M=M+1`（RAM[256]=2，SP=257）。再 push 3：RAM[257]=3，SP=258。`add`：弹 3（y）到 D，SP 指向 256，`M=D+M` → RAM[256]=5，SP=257。
- **最终答案**：`add` 模板：`@SP; AM=M-1; D=M; A=A-1; M=D+M`——注意 `AM=M-1` 同时完成"SP 减 1"与"取新栈顶地址"，A 寄存器两用。
- **易错点**：二元操作的**操作数顺序**：先弹的是 y（右操作数），后弹的是 x；`sub` 是 x−y 不是 y−x。**🤔 追问**：`sub` 模板最后是 `M=M-D`，若搞反顺序，`2-3` 会算成 `3-2`。

### 例子 2：中等例子（条件判断与多步推理）
- **题目**：翻译 `lt`（x < y），并说明为什么不能直译成 Hack 的 `JLT`。
- **解题思路与完整解答**：先弹 y、弹 x，算 `D = x - y`（`D=M-D`），然后"D<0 时把结果写 -1，否则写 0"：`@SP; AM=M-1; D=M; A=A-1; D=M-D; M=0; @LT_1; D;JLT; @END_1; 0;JMP; (LT_1) @SP; A=M-1; M=-1; (END_1)`。**关键推理**：Hack 的 `JLT` 只能"跳转"，而 VM 的 `lt` 要"产生布尔值放回栈"，所以必须"算差 → 条件跳转填 -1 → 否则留 0"两步；标签 `LT_1/END_1` 的编号是为了多个 `lt` 不共用标签。
- **易错点**：忘记把结果写回栈顶（`A=M-1` 再 `M=-1`）；两个标签忘记编号导致汇编器报重复标签。

### 例子 3：实际应用例子（真实场景/代码）
- **实际价值与转化**：官方 `SimpleFunction.test`（HW08）与 `Sys.vm` 验证整条调用链；`factorial` 递归程序在 VM Emulator 上逐帧观察——每次递归调用都新压一帧（实参+返回地址+旧 LCL/ARG/THIS/THAT），深度 N 时栈上有 N 帧，这正是"递归 = 栈的自然行为"的直观证据。
- 代码形态（`function` 与 `return` 的核心片段）：
```asm
// function SimpleFunction.test 2  →  初始化 2 个 local 为 0
(SimpleFunction.test)
@SP; A=M; M=0; @SP; M=M+1   // local 0 = 0
@SP; A=M; M=0; @SP; M=M+1   // local 1 = 0
// return: FRAME=LCL; RET=*(FRAME-5); *ARG=pop(); SP=ARG+1; THAT=*(FRAME-1); THIS=*(FRAME-2); ARG=*(FRAME-3); LCL=*(FRAME-4); goto RET
```

## 8. 常见误区和易混概念

### 误区 1：比较指令可以直接用 Hack 的 JLT/JEQ/JGT 翻译
- **错误直觉**：VM 的 `lt` 对应 Hack 的 `JLT`，一行搞定。**为什么错**：`JLT` 只是"跳转"，而 VM 的 `lt` 要**产生一个布尔值（0 或 -1）压回栈**，且要先弹两个操作数做差；直接跳转会丢掉"结果值"。
- **正确理解**：比较 = "算差 + 条件填值"两段式，还要为每个比较生成唯一编号标签。

### 误区 2：pop 时"先减 SP 再取址"与"先取址再减"无所谓
- **错误直觉**：`@SP; M=M-1; A=M; D=M` 和 `@SP; A=M-1; D=M; @SP; M=M-1` 一样。**为什么错**：SP 指向**栈顶上空位**（下一个可写位置）；取栈顶必须用 `SP-1`，顺序错了会弹到空位或残留旧值。
- **正确理解**：`AM=M-1` 是官方模板的核心技巧：一条指令同时"减 SP"并"把 A 设为新栈顶"。

### 误区 3：return 时恢复现场的顺序随便写
- **错误直觉**：恢复 THAT/THIS/ARG/LCL 四条指针，先后无所谓。**为什么错**：恢复 LCL/ARG 之后 `FRAME` 基址就丢了——必须先取 `FRAME = LCL`、`RET = RAM[FRAME-5]` 存好，再恢复指针，最后 `goto RET`。
- **正确理解**：return 顺序是"先取 RET → 放返回值 → 重设 SP → 恢复 THAT/THIS/ARG/LCL → 跳转"，任何一步提前都会丢信息。

### 概念对比表

| 概念 | 核心问题 | 关键区别 | 典型使用场景 |
| :--- | :--- | :--- | :--- |
| 栈机 vs 寄存器机 | 临时值放哪 | 显式栈 vs 寄存器文件 | VM/JVM/WebAssembly vs x86/ARM |
| VM 语言 vs 汇编 | 抽象层次 | 段寻址+函数 vs 裸地址+跳转 | HW07-08 输入 vs 输出 |
| call vs function | 谁负责建帧 | 调用方压返回地址/旧帧 vs 被调方分配局部变量 | HW08 翻译 |

### 题目与解析

#### 1. 为什么"操作数栈"能同时支撑表达式求值与函数调用？
> [!question]- 答案解析
> - **答案**：两者都是"嵌套结构"：表达式最内层先算、函数最内层先返回，天然是后进先出；栈恰好以同一机制（压栈/弹栈）承载中间结果与调用帧。
> - **解析**：这是"一个机制两用"的经典案例——VM 只需维护一个 SP 指针，就能同时描述"算到哪了"与"调用到哪层了"。易错：把表达式栈与调用栈想成两个独立结构，其实共享同一 SP。

#### 2. 执行 `push constant 2; push constant 3; sub` 后栈顶值是多少？写出翻译模板。
> [!question]- 答案解析
> - **答案**：栈顶 = 2 − 3 = **-1**（补码 1111111111111111）；`sub` 模板：`@SP; AM=M-1; D=M; A=A-1; M=M-D`。
> - **解析**：先弹 y=3，再弹 x=2，结果 x−y = −1。易错：写成 `M=D-M` 则得 1——操作数顺序是 VM 算术翻译的第一大坑。

#### 3. 翻译 `eq` 时为什么要生成两个标签（如 `EQ_1`/`END_1`）？编号有什么用？
> [!question]- 答案解析
> - **答案**：`eq` 需要"算差 D=x−y；若 D=0 则把栈顶写 -1，否则保持 0"——这是条件跳转，必须有跳转目标；编号（计数器后缀）保证同一程序里多个 `eq` 不共用标签，否则汇编器报重复定义。
> - **解析**：Hack 没有"按条件产生值"的指令，只有"按条件跳转"，所以"填值"必须借助跳转+标签。易错：多个比较指令共用同一标签。

#### 4. `call Main.factorial 1` 执行后，ARG 与 LCL 分别指向哪里？帧里从低到高存了什么？
> [!question]- 答案解析
> - **答案**：设调用前 SP=S：先依次压入返回地址、LCL、ARG、THIS、THAT（5 个字），再压 1 个实参；随后 `ARG = SP-5-1`（指向实参）、`LCL = SP`（指向保存的 THAT 之后）。帧从低到高：实参 → 返回地址 → 旧 LCL → 旧 ARG → 旧 THIS → 旧 THAT → 局部变量区。
> - **解析**：`return` 用 `RAM[LCL-5]` 取返回地址、`RAM[LCL-k]` 恢复指针，正是因为这个固定布局。易错：忘记 call 先压实参、后压 5 个现场字，导致 ARG 偏移算错。

#### 5. 手推 `factorial(3)` 在 VM 上的执行：递归深度为 3 时栈上有几帧？每帧包含什么？为什么返回时能回到正确位置？
> [!question]- 答案解析
> - **答案**：3 帧（外加 Sys.init 的调用帧共 4 层）。每帧 = 实参 n + 返回地址 + 旧 LCL/ARG/THIS/THAT + 局部变量。返回时 `return` 用 `FRAME=LCL`、`RET=RAM[FRAME-5]` 取出该帧自己的返回地址，恢复旧指针后跳转——每帧都完整记录了"我该回哪、我的调用者现场是什么"。
> - **解析**：递归之所以在栈机上"自然成立"，是因为每次调用都新建独立帧、不覆盖任何旧数据；深度 N 的递归 = N 层嵌套的"档案柜"。易错：以为递归需要特殊处理——不需要，调用约定对递归与普通调用一视同仁。
