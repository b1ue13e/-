# 优化层次 (Algorithm → Code → Compiler → Architecture → System)

## 1. 为什么学：优化不是"调一个参数"

性能优化的第一原则是**先找到瓶颈，再选对层次**。这张卡建立优化的五层框架（算法/代码/编译器/架构/系统），回答"这个优化应该在哪一层做、收益有多大、风险是什么"。这是本阶段所有优化技术卡的导航图。

## 2. 五层优化框架

| 层次 | 手段 | 典型收益 | 风险 |
|:---|:---|:---|:---|
| **算法层** | 换算法、降复杂度 | 数量级（O(n²)→O(n log n)） | 实现重写、正确性 |
| **代码层** | 循环展开、消除冗余、数据布局 | 常数倍（2-10x） | 可读性、编译器干扰 |
| **编译器层** | O2/O3、内联、向量化 | 常数倍 | 编译时间、可移植性 |
| **架构层** | SIMD、缓存友好、并行 | 10-100x（硬件特性） | 平台绑定、复杂度 |
| **系统层** | 系统调用优化、I/O 合并、内核参数 | 取决于负载 | 运维复杂度 |

## 3. 优化方法论（先测量，再优化）

### 3.1 自上而下 vs 自下而上

| 方法 | 思路 | 适用 |
|:---|:---|:---|
| **自上而下（Top-Down）** | 从系统级指标（吞吐/延迟）逐层下钻定位瓶颈 | 先判断瓶颈在 CPU/内存/IO/网络 |
| **自下而上（Bottom-Up）** | 从硬件计数器/工具细节向上推断 | 已知热点后深挖 |

### 3.2 关键指标

| 指标 | 含义 | 瓶颈信号 |
|:---|:---|:---|
| **CPU 利用率** | 核的忙碌比例 | <70% 可能等待 I/O/锁 |
| **IPC（每周期指令数）** | 流水线效率 | 低 IPC = 停顿多（依赖/缺失） |
| **缓存命中率** | 缓存效率 | 低命中率 → 内存墙 |
| **上下文切换** | 内核调度开销 | 频繁切换 → 线程过多 |
| **分支预测率** | 流水线冲刷频率 | 低预测率 → 控制冒险 |

## 4. 性能权衡（Trade-offs）

| 权衡 | 本质 | 例子 |
|:---|:---|:---|
| **延迟 vs 吞吐** | 单任务时间 vs 总任务量 | 流水线（延迟↑吞吐↑） |
| **空间 vs 时间** | 内存换速度 | 缓存、预计算表 |
| **公平 vs 效率** | 调度均衡 vs 总量最大 | CPU 调度策略 |
| **计算 vs 存储** | 重算还是缓存结果 | 动态规划 vs 记忆化 |

## 5. 常见误区（反例）

- **误区 1**："优化从代码层开始"——应先测量确定瓶颈层，可能瓶颈在算法（要换算法）而非代码；
- **误区 2**："IPC 高 = 性能好"——IPC 依赖指令集和负载特征，跨架构比较无意义；
- **误区 3**："每个优化都值得做"——过早优化是万恶之源；优化应针对测量到的真实热点（Pareto：20% 代码占 80% 时间）。
