## 0. 先判断它值不值得深挖

- **类别**：**A 类（核心概念，必须深挖）**
- **判断理由**：在大语言模型（LLM）时代，提示工程是与模型交互、挖掘模型潜力的最直接和最有效的方式。它不需要更新模型参数，仅通过设计输入文本就能极大提升模型在复杂任务（如推理、数学、代码）上的表现。对于任何使用或研究 LLM 的人来说，这是基础且必不可少的技能。

---

## 1. 这个知识点解决什么问题？

> **我们遇到了什么麻烦**：
> 传统的预训练语言模型（如早期的 GPT）虽然学习到了海量的知识，但它们的目标只是“预测下一个词”。当我们直接向它提问或让它完成特定任务时，它可能会顺着问题继续生成毫无意义的文本，或者无法理解我们需要它做多步骤推理。我们不能每次为了一个新任务就去微调（Fine-tune）一个庞大的模型（成本太高且不灵活），我们需要一种轻量级的方法，用自然语言去“引导”模型直接输出正确答案。

---

## 2. 为什么它重要？它有什么用？

- **连接大图景**：它是连接基础大模型（Foundation Models）与下游实际应用的核心桥梁。不掌握 Prompt Engineering，就无法理解目前最火的 Agent 架构、RAG（检索增强生成）系统以及复杂的多步推理系统是如何运转的。
- **实际应用场景**：在开发 LLM 应用（如聊天机器人、智能客服、文档自动摘要、代码生成工具）中，通过设计系统提示词（System Prompt）和用户提示词（User Prompt）来控制模型输出的格式、语气和准确性。
- **高频题型/任务**：文本分类、信息抽取、机器翻译、逻辑推理、代码编写与调试等几乎所有 NLP 任务。

## 5. 正式定义、核心公式、符号解释

### 1. 最核心定义
**提示工程（Prompt Engineering）** 是一种通过设计和优化输入文本（Prompt），以最大化大语言模型在特定任务上性能的技术。它包括零样本（Zero-shot）、少样本（Few-shot）提示，以及思维链（Chain of Thought, CoT）等高级技巧。

### 2. 核心公式与 Tensor Tracking
从概率分布的角度，Prompting 本质上是条件语言模型生成：
$$\hat{y} = \arg\max_{y} P(y | x, p, \theta)$$

对于 Few-shot In-Context Learning，公式可以写为：
$$P(y | x, E_1, E_2, \dots, E_k, \theta)$$

**【Academic Hardcore: Heuristic-based Prompt Tracking & Tensor Flow】**
为了直观理解 Prompt 是如何在模型前向传播中发挥作用的，我们可以追踪其 Tensor 维度的变化：
假设拼接后的 Prompt 序列长度为 $L_{prompt}$，当前已生成的序列长度为 $L_{gen}$，总长度 $L = L_{prompt} + L_{gen}$。
- **Input Tokens**: `[B, L]` （B为Batch Size，通常为1）
- **Embedding Layer**: `[B, L] -> [B, L, d_model]`
- **Self-Attention 阶段**: 
  - $X$: `[B, L, d_model]`
  - 映射为 $Q, K, V$: `[B, h, L, d_k]`，其中 $h$ 为注意力头数，$d_k = d_{model} / h$
  - **Attention Scores**: $Attention(Q, K, V) = \text{softmax}\left(\frac{QK^T}{\sqrt{d_k}}\right)V$
  - **为何除以 $\sqrt{d_k}$？**：由于 $Q$ 和 $K$ 的元素通常服从独立同分布（均值0，方差1），其点积 $Q K^T$ 的方差会随 $d_k$ 成比例放大（即方差为 $d_k$）。如果方差过大，进入 softmax 后会导致梯度消失（softmax 输出趋于 one-hot）。除以 $\sqrt{d_k}$ 可将其方差拉回 1，保证梯度平稳流过，这直接关系到模型能否准确捕捉极长 Few-shot Prompt 中的上下文依赖。
- **Output of Block**: `[B, L, d_model]` -> 投影到词表维度 `[B, L, V_{vocab}]` 取最后一位做 Argmax。

### 3. 符号说明表

| 符号 | 含义 | 取值范围 / 量纲 | 备注 |
| :--- | :--- | :--- | :--- |
| $x$ | 输入文本/问题 | 词表序列 | 用户实际要问的问题 |
| $p$ | 提示词前缀 | 词表序列 | 包含指令、系统设定等 |
| $y$ | 模型生成的输出 | 词表序列 | 期望的答案 |

| $\theta$ | 模型参数 | $\mathbb{R}^p$ | 在 Prompting 中参数被冻结，不更新 |

### 4. 常见变体与适用条件
- **Zero-shot Prompting**：直接给指令，不给例子。适用于模型已经非常熟悉的基础任务（如翻译）。
- **Few-shot Prompting (In-Context Learning)**：给几个 `(输入, 输出)` 示例。适用于特定格式输出或未见过的新奇子任务，受限于上下文窗口大小。
- **Chain of Thought (CoT)**：要求模型展示中间推理过程。适用于数学、逻辑、常识推理等复杂任务。

## 6. 推导思路和思想来源

- **最初困难**：GPT-2 时代，研究者发现大模型具有一定的零样本能力，但由于缺乏明确指令，性能极不稳定。微调每个任务成本又太高。
- **直接方法局限**：Fine-tuning 需要大量标注数据，且会改变模型权重，容易导致灾难性遗忘。
- **关键“转念”**：既然大模型在预训练时看过了海量网页，其中包含了很多“一问一答”或“一步步推导”的模式。为何不直接在输入中模拟这种模式，让模型在**不更新参数**的情况下，通过前向传播在上下文中（In-Context）动态“学习”如何做这个任务？
- **推导主线与动机**：GPT-3 论文正式提出 In-Context Learning。随后，Chain of Thought（思维链）被提出，发现只要在 Prompt 中加入中间推理步骤，模型就能解决以前无法解决的复杂数学题。
- **为什么自然得到此结论**：因为 transformer 的 self-attention 可以让当前正在生成的词去关注前面输入中的示例（Few-shot）或者刚刚自己生成的中间步骤（CoT），从而保证逻辑的连贯性。

## 7. 例子：基础 → 中等 → 实际应用

### 例子 1：基础例子（Few-shot Prompting）
- **题目**：让模型判断电影评论的情感倾向，并强制输出 JSON 格式。
- **解题思路与关键步骤**：提供几个标注好的例子（In-Context Learning）。
- **最终答案**（Prompt）：
  ```text
  将以下电影评论分类为"Positive"或"Negative"，并以 JSON 格式输出 {"sentiment": "..."}。

  评论: "这电影太棒了，特效惊人！"
  输出: {"sentiment": "Positive"}

  评论: "剧情拖沓，看得我睡着了。"
  输出: {"sentiment": "Negative"}

  评论: "演员演技在线，但导演没讲好故事。"
  输出:
  ```
- **易错点**：给的例子格式必须一致，否则会导致模型输出混乱。
- **🤔 追问**：如果例子里的标签分布不均衡（比如全是 Positive），会怎样？（答：模型会产生偏差，倾向于预测 Positive）。

### 例子 2：中等例子（Chain of Thought, CoT）
- **题目与完整解答**：
  解决数学应用题：“食堂有 23 个苹果。如果他们用 20 个做午餐，然后又买了 6 个，现在有多少个苹果？”
  **CoT Prompt**：
  ```text
  问：食堂有 23 个苹果。如果他们用 20 个做午餐，然后又买了 6 个，现在有多少个苹果？
  答：食堂一开始有 23 个苹果。用 20 个做午餐后，剩下 23 - 20 = 3 个。又买了 6 个，所以现在有 3 + 6 = 9 个苹果。答案是 9。

  问：小明有 5 个网球，他又买了两罐网球，每罐有 3 个。小明现在有多少个网球？
  答：
  ```

### 例子 3：实际应用例子（系统级指令与角色扮演）
- **实际价值与转化**：在开发 AI 助手时，设定其行为边界。
  ```text
  System Prompt:
  你是一位资深 Python 架构师。你的任务是审查用户提交的代码。
  请遵循以下规则：
  1. 先指出代码中的安全漏洞（如果有）。
  2. 然后提供重构建议，确保符合 PEP 8。
  3. 最后给出修改后的完整代码。
  不要使用居高临下的语气。

  User: [代码]
  ```

## 8. 常见误区和易混概念

### 误区 1：Prompt Engineering 就是玄学/咒语
- **错误直觉**：认为找到某个神奇的词就能解决所有问题。
- **为什么错**：模型的表现取决于预训练数据的分布和注意力机制在上下文中的激活情况。
- **正确理解**：提示工程是一门基于实验、有系统方法论（清晰指令、示例、分解步骤）的工程。

### 概念对比表

| 概念 | 核心问题 | 关键区别 | 典型使用场景 |
| :--- | :--- | :--- | :--- |
| Fine-tuning (微调) | 模型知识或风格不足 | 改变参数 $\theta$ | 注入大量垂直领域知识 |
| In-Context Learning | 快速适配新任务格式 | 不改变参数，仅靠上下文 | 快速原型，输出格式规范化 |
| RAG (检索增强生成) | 模型存在幻觉，缺乏最新知识 | 外挂知识库放入 Prompt | 问答系统，企业知识库 |

### 题目与解析

#### 1. [题目 1：Zero-shot CoT]
> [!question]- 答案与解析（复盘阶段查看）
> - **答案**：在 prompt 末尾加上 "Let's think step by step."。
> - **解析**：这句话激活模型在预训练时见过的推导语料，使其开始输出中间过程，提高准确率。

#### 2. [题目 2：设计抽取 Prompt]
> [!question]- 答案与解析（复盘阶段查看）
> - **问题**：设计一个 Prompt，从新闻中抽取人名，没有则输出 "None"。
> - **易错原因**：如果没有提供反例（即没有提到人的新闻）的 Few-shot，模型容易产生幻觉。

#### 3. [题目 3：API 消息结构]
> [!question]- 答案与解析（复盘阶段查看）
> - **答案**：利用 roles 构建 Few-shot：
>   ```json
>   [
>     {"role": "system", "content": "情感分析器，仅输出 Positive 或 Negative。"},
>     {"role": "user", "content": "太好看了！"},
>     {"role": "assistant", "content": "Positive"}
>   ]
>   ```

#### 4. [题目 4：解决幻觉]
> [!question]- 答案与解析（复盘阶段查看）
> - **解析**：在 prompt 中加入约束，如：“仅根据提供的信息回答。如果不知道请直接回答‘我不知道’。”

#### 5. [题目 5：Prompt 越长越好吗？]
> [!question]- 答案与解析（复盘阶段查看）
> - **解析**：不是。长文本会导致模型出现“Lost in the Middle”现象，忽略中间信息。应保持核心要素前置。
