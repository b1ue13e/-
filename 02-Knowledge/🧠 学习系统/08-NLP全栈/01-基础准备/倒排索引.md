# 倒排索引
---
## 0. 先判断它值不值得深挖
- **类别**：**B 类（常用工具）**
- **判断理由**：它是"给机器一份能秒答'哪篇文档提到 XX'的预计算名单"，是第一阶段"简单搜索引擎"项目的核心数据结构，也是 [[检索增强生成RAG]] 召回阶段的远古原型（现在换成向量，但"用索引换时间"的思想不变）。本卡讲透**构建、布尔合并、跳跃表、短语查询**四件事；同一主题在 [[02-Knowledge/🧠 学习系统/36-数据挖掘与信息检索/倒排索引与布尔检索|倒排索引与布尔检索（信息检索路径·A 类深挖版）]] 有完整推导与作业对接，两卡互补。
---
## 1. 这个知识点解决什么问题？
> **我们遇到了什么麻烦**：
> 语料里躺着几十万篇文档，老板让你回答"哪些文档同时提到『深度学习』和『倒排索引』"。最笨的办法是把每篇文档从头读一遍（**顺序扫描**）——查一次要 $O(N)$ 次比较，语料一涨查询就崩。
> 倒排索引的回答：**提前把"词 → 文档列表"算好存起来**（就像书末的术语索引），查询时直接取出两份名单做**集合合并**，复杂度从"扫全库"降到"只碰命中的名单"。再配上**跳跃表**加速合并、**位置列表**支持短语查询，就凑齐了一个迷你搜索引擎的全部零件。
---
## 2. 为什么它重要？它有什么用？
- **连接大图景**：第一阶段数据结构课的收官应用（词典 → Trie → 倒排表是一条线）；[[文本表示方法]] 里 TF-IDF 的 df（文档频率）就来自倒排表的表项长度；[[检索增强生成RAG]] 的稀疏检索（BM25/ES）底层仍是它；[[信息抽取]] 的候选召回也常用它。
- **实际应用场景**：Elasticsearch / Lucene 的存储核心；面试高频题"倒排索引怎么支持短语查询""跳跃表合并为什么快"。
- **高频题型/任务**：词项-文档矩阵 ↔ 倒排表互转；AND/OR/NOT 合并手推；跳跃表步长计算；用位置列表做短语查询。

## 4. 用直觉语言解释它
> «"倒排索引就像书末的术语索引"：想找『倒排』出现在哪些页，你不会从第 1 页翻起，而是直接翻到索引页，看到"倒排 … 45, 120, 233"。倒排表就是每个词后面挂的那串页码（文档 ID），布尔查询就是同时翻几个词的页码列表，把相同的页码圈出来。"»
- **直觉类比/几何图像**：词项-文档矩阵是"行=词项、列=文档"的 0/1 稀疏矩阵（大多数格子是 0）；倒排表就是**按行压缩**——每行只存非零元的列号。矩阵越稀疏，压缩收益越大。
- **为什么很自然**：查询永远从"词"出发，那就把数据预组织成"按词索引"；文档 ID 天然可排序，排序后就能用双指针/跳跃表合并。
- **一句话直觉本质**：**"把『文档 → 词』反转为『词 → 有序文档列表』，用空间换时间；查询 = 列表合并；加位置列表 = 短语查询。"**
---
## 5. 正式定义、核心公式、符号解释
### 1. 最核心定义
- **词项-文档矩阵**：$M \in \{0,1\}^{|V|\times N}$，$M_{t,d}=1$ 当且仅当词项 $t$ 出现在文档 $d$；$V$ 为词表，$N$ 为文档总数。
- **倒排索引**：对每个词项 $t$ 维护**倒排表** $P_t=[d_1,\dots,d_{f_t}]$（按 docID 升序），$f_t$ 为该词的**文档频率 df**；位置级倒排表项再挂 (词频 tf, 位置列表 $[p_1,\dots]$)。
- **布尔查询**：查询被解析为词项的 AND/OR/NOT 表达式，对倒排表做集合交/并/差。
### 2. 核心公式
$$P_{t_1}\cap P_{t_2}:\ \text{双指针合并，代价 } O(|P_{t_1}|+|P_{t_2}|)$$
$$\text{跳跃表步长 } \text{skip}=\lfloor\sqrt{L}\rfloor,\quad L=\text{倒排表长度（平衡比较次数与跳过开销）}$$
$$\text{短语查询：位置匹配 } \bigcap_t \{\,d : \exists p,\ p\in\text{pos}_{t_1}(d),\ p+1\in\text{pos}_{t_2}(d)\,\}$$
### 3. 符号说明表
| 符号 | 含义 | 取值范围 / 量纲 | 备注 |
| :--- | :--- | :--- | :--- |
| $V$ | 词表（词项集合） | $\approx 10^5$–$10^6$ | 分词+停用词后 |
| $N$ | 文档总数 | $10^4$–$10^9$ | 语料规模 |
| $P_t$ | 词项 $t$ 的倒排表 | 长度 $f_t$ | 按 docID 升序 |
| $f_t$ / df | 文档频率 | $1\le f_t\le N$ | 与 IDF 挂钩 |
| tf | 词项在单篇文档中的次数 | $\ge 1$ | 位置级索引才有 |
| $\text{pos}_t(d)$ | 词项 $t$ 在文档 $d$ 中的位置列表 | 升序整数 | 短语查询依据 |
### 4. 常见变体与适用条件
- **文档级倒排**（只存 docID）：布尔查询够用，省空间。
- **位置级倒排**（docID + tf + 位置列表）：支持短语查询与邻近查询；空间膨胀 2–4 倍。
- **适用/限制条件**：适合语料相对静态、查询是关键词/布尔表达式；纯布尔模型**不排序**（命中即等权），NOT 查询需与全集 $N$ 做差集代价高，词典需常驻内存（见 [[Trie树]] 压缩方案）。

## 6. 推导思路和思想来源
- **最初困难**：顺序扫描 $O(N)$ 无法支撑海量文档；朴素"文档 → 词"正向索引只能回答"这篇文档有什么词"，答不了"哪个文档有这个词"；词项-文档矩阵又太稀疏，直接存储浪费空间。
- **关键"转念"**：① **反转**——把矩阵按列（词项）组织，只存非零元，查询直达；② **排序**——倒排表按 docID 升序，使合并可用双指针线性扫描；③ **跳跃**——给倒排表加"每隔 $\sqrt{L}$ 个元素一个跳指针"，合并时大步越过不可能匹配的区间；④ **加位置**——表项里多存一份位置列表，短语查询从"文档级交集"升级为"位置级相邻匹配"。
- **推导主线与动机**：顺序扫描 → 正向索引 → 倒排索引（反转+压缩）→ 有序合并（双指针）→ 跳跃表（加速）→ 位置列表（短语查询）。每一步都只解决上一步的一个具体瓶颈。
- **为什么自然得到此结论**：查询入口是"词"，数据出口是"文档集合"，把入口做成索引是信息检索最自然的组织方式；有序结构让所有运算（合并、跳过、位置匹配）都能用二分/双指针套路。

## 7. 例子：基础 → 中等 → 实际应用
### 例子 1：基础例子（可手算）
- **题目**：3 篇微型文档：D1="猫 吃 鱼"，D2="狗 吃 肉"，D3="猫 吃 老鼠"。建文档级倒排索引。**思路**：分词 → 每词收集出现过的 docID → 去重后升序。
- **最终答案**：猫→[1,3]；吃→[1,2,3]；鱼→[1]；狗→[2]；肉→[2]；老鼠→[3]。
- **易错点**：一个词在一篇文档出现多次，文档级索引只记一次（df 按文档计数，不是按次数）；位置级才记 tf 与位置。
- **🤔 追问**：查询"猫 AND 吃"的结果？—— 合并 [1,3] 与 [1,2,3] → [1,3]；"猫 AND 狗"→ 空集 ∅。
### 例子 2：中等例子（条件判断与多步推理）
- **题目与完整解答**：$P_{\text{猫}}=[1,3]$、$P_{\text{吃}}=[1,2,3]$、$P_{\text{狗}}=[2]$，跳跃表步长各是多少？合并"猫 AND 狗"用双指针要走几步？—— 步长 $\lfloor\sqrt{2}\rfloor=1$、$\lfloor\sqrt{3}\rfloor=1$：表太短，跳跃无收益（步长至少 2 才划算）。双指针：i=1 vs j=2 → 不等，j 前进；i=3 vs j=2 → 不等，i 前进到末尾 → 2 步比较，结果 ∅。结论：**跳跃表只在长倒排表（$L\gtrsim 4$）上才有加速价值**，短表直接线性合并。
### 例子 3：实际应用例子（真实场景/代码）
- **实际价值与转化**：用 Python 实现"构建 + 布尔合并 + 短语查询"迷你引擎：
```python
from collections import defaultdict

def build_index(docs):               # 词 -> [(docID, pos)]
    idx = defaultdict(list)
    for doc_id, text in enumerate(docs):
        for pos, w in enumerate(text.split()):
            idx[w].append((doc_id, pos))
    return idx

def intersect(a, b):                 # 双指针 AND 合并（表已升序）
    i = j = 0; r = []
    while i < len(a) and j < len(b):
        if a[i] == b[j]: r.append(a[i]); i += 1; j += 1
        elif a[i] < b[j]: i += 1
        else: j += 1
    return r

def phrase(idx, w1, w2):             # 短语查询："w1 w2" 位置相邻
    return sorted({d for d, p in idx[w1] if any(d2 == d and p2 == p + 1 for d2, p2 in idx[w2])})

docs = ["猫 吃 鱼", "狗 吃 肉", "猫 吃 老鼠"]
idx = build_index(docs)
print(intersect([d for d, _ in idx["猫"]], [d for d, _ in idx["吃"]]))  # [0, 2]
print(phrase(idx, "吃", "鱼"))                                          # [0]
```

## 8. 常见误区和易混概念
### 误区 1：以为"倒排表就是词频统计"
- **错误直觉**：倒排表 = 每个词出现多少次。
- **为什么错**：文档频率 df 数的是**文档**（去重），词频 tf 数的是**出现次数**；文档级倒排表根本不含 tf。把 df 当 tf 会算错 IDF 与 BM25 权重。
- **正确理解**：倒排表的单位是"文档 ID（+ 可选位置）"，频率是附加统计量。
### 误区 2：以为"布尔检索能给出相关性排序"
- **错误直觉**：搜"猫 吃"返回的结果是按相关度排好的。
- **为什么错**：纯布尔模型只有"命中/未命中"，结果等权无序（第 4 节限制条件）；排序需要向量空间模型或 BM25（见 [[文本表示方法]]）。
- **正确理解**：布尔检索负责"筛"，排序模型负责"排"，是两件事。
### 概念对比表
| 概念 | 组织方向 | 回答的问题 | 典型使用场景 |
| :--- | :--- | :--- | :--- |
| 倒排索引（本概念） | 词 → 文档列表 | 哪些文档含词 t | 搜索/召回 |
| 正向索引 | 文档 → 词列表 | 文档 d 含哪些词 | 文档处理流水线 |
| 向量数据库 | 向量 → 近邻文档 | 语义相似文档 | RAG 稠密召回 |

### 题目与解析
#### 1. 倒排索引里"文档频率 df"与"词频 tf"有什么区别？
> [!question]- 答案解析
> - **答案**：df 统计"词出现在多少篇不同文档中"（去重），tf 统计"词在一篇文档中出现多少次"。文档级倒排表只含 df 对应信息，tf 只在位置级表项中出现。
> - **解析**：混淆二者会导致 IDF/BM25 权重算错。`#自测题/基础`
#### 2. 已知 $P_{\text{a}}=[1,2,5,9]$、$P_{\text{b}}=[2,4,9,11]$，手推 AND 合并结果与比较次数。
> [!question]- 答案解析
> - **答案**：双指针：1<2→i++；2=2→命中，i++、j++；4<5→j++；5<9→i++；9=9→命中；结束。结果 [2,9]，共 7 次比较（4+4-1）。
> - **解析**：最坏 $O(|A|+|B|)$，最好情况命中多时更快。`#自测题/基础`
#### 3. 什么情况下跳跃表合并没有收益？
> [!question]- 答案解析
> - **答案**：倒排表很短（$L<4$，步长 $\lfloor\sqrt{L}\rfloor\le1$ 退化为线性）、或两表长度悬殊、或查询词高频（df 极大）时，跳跃的"跳空"机会少，反而多维护指针。
> - **解析**：跳跃表是"比较次数 vs 指针开销"的权衡，长表+低频词收益最大。`#自测题/中等`
#### 4. 如何用位置级倒排表回答短语查询"深度学习 模型"？
> [!question]- 答案解析
> - **答案**：先对两词倒排表做文档级交集得候选文档；对每个候选文档 $d$，检查是否存在位置 $p$ 使 $p\in\text{pos}_{\text{深度学习}}(d)$ 且 $p+1\in\text{pos}_{\text{模型}}(d)$；存在则 $d$ 命中。
> - **解析**：相邻位置匹配就是"短语"的定义；若允许多间隔 k，则检查 $p+k$，得到邻近查询。`#自测题/中等`
#### 5. 对比"顺序扫描、倒排索引、向量数据库"三种检索方案的适用场景。
> [!question]- 答案解析
> - **答案**：顺序扫描：语料小（<10^4）或一次性批处理，零构建成本；倒排索引：关键词/布尔/短语查询、语料静态，毫秒级精确命中；向量数据库：语义相似召回（RAG 场景），需要 embedding 与 ANN 索引，牺牲精确性换语义泛化。
> - **解析**：三者不是替代而是演进关系——倒排解决"精确词匹配"，向量解决"语义匹配"，现代搜索系统两者混合使用。`#自测题/较难`
