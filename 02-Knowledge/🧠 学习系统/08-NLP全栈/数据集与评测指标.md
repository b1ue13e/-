# 数据集与评测指标

---

## 0. 先判断它值不值得深挖

- **类别**：**A 类（核心概念，必须深挖）**
- **判断理由**：评测是每一份作业的"验收标准"：HW02 分类看 Acc/F1、HW04 翻译看 BLEU、HW05 看 SST-2 Acc、语言模型看困惑度。不会选指标、不会解读指标，作业"过了"还是"没过"都无法判断；GLUE 是预训练模型的标准战场。

---

## 1. 这个知识点解决什么问题？

> **我们遇到了什么麻烦**：
> 模型训练完了，怎么知道它"好不好"？直接用准确率有陷阱：类别不平衡时（99% 负面、1% 正面），"全猜负面"的模型准确率 99% 但毫无用处；翻译任务"逐字比对"会惩罚同义表达（"猫坐在垫子上" vs "垫子上有只猫"都算错）；语言模型"预测对下一个词"的概率该怎么量化？
> 因此需要一组**任务匹配的评测指标**：分类任务用准确率/精确率/召回/F1；生成任务用 BLEU/ROUGE（n-gram 重叠）；语言模型用困惑度；综合能力用 GLUE/SuperGLUE 基准——每个指标回答"这个任务上，模型做到什么程度"。

---

## 2. 为什么它重要？它有什么用？

- **连接大图景**：HW02 的 F1 报告、HW04 的 BLEU 验收、HW05 的 SST-2 Acc 与 GLUE 基准、[[GPT系列]] 的困惑度——评测贯穿全部作业与论文阅读；[[HuggingFace生态系统]] 的 `evaluate` 库就是指标工程化。
- **实际应用场景**：模型选型（对比不同 checkpoint）、论文实验、上线前验收（准确率+错误分析）、LLM 评测（GLUE/MMLU/人工偏好）。
- **高频题型/任务**：手算 F1/BLEU；解释"准确率在类别不平衡时的失效"；困惑度与交叉熵的关系；GLUE 包含哪些任务（SST-2/MNLI/QQP 等）。

---

## 3. 学它之前需要哪些前置知识？

1. **混淆矩阵**：TP/FP/FN/TN 四格定义是 P/R/F1 的源头。
2. **交叉熵与信息论**：困惑度 = $e^{\text{交叉熵}}$，需要理解熵与概率。
3. **[[文本预处理]]**：n-gram 是 BLEU/ROUGE 的计算单位。

---

## 4. 用直觉语言解释它

> «"评测指标就像不同运动的计分规则：足球看进球数（准确率——简单直观但只适合'大多数情况'），篮球看命中率还要分两分三分（精确率/召回——区分'说的准'和'找得全'），花样滑冰看裁判综合分（BLEU/ROUGE——机器翻译没有唯一标准答案，只能比'和参考译文的相似度'）。选错计分规则，比赛结果毫无意义——所以先想清楚'这个任务什么算赢'。"»

- **直觉类比/几何图像**：精确率 = "我说对的东西里有多少是真对的"（宁缺毋滥）；召回率 = "真正该找到的东西里我找到了多少"（宁滥勿缺）；F1 是两者的调和平均——"两个都要，取平衡"。
- **为什么很自然**：BLEU 用 n-gram 重叠衡量翻译质量，是因为"好翻译与参考译文用词相近"是弱但可算的代理指标；困惑度"模型给真实下一个词的概率的倒数"直接对应"模型有多不确定"。
- **一句话直觉本质**：**为每个任务选"与目标一致且可计算"的度量：分类用混淆矩阵派生的 P/R/F1，生成用 n-gram 重叠（BLEU/ROUGE），语言模型用困惑度，综合能力用基准榜（GLUE）。**

---

## 5. 正式定义、核心公式、符号解释

### 1. 最核心定义
**混淆矩阵**：TP（真正例）、FP（假正例）、FN（假负例）、TN（真负例）。

**准确率 / 精确率 / 召回率 / F1**：
$$\text{Acc} = \frac{TP+TN}{TP+FP+FN+TN},\quad P = \frac{TP}{TP+FP},\quad R = \frac{TP}{TP+FN},\quad F1 = \frac{2PR}{P+R}$$

**困惑度（Perplexity）**：
$$\text{PPL} = \exp\left(-\frac{1}{T}\sum_{t=1}^{T}\log P(w_t \mid w_{<t})\right) = 2^{H}$$

**BLEU**（n-gram 精确率 + 长度惩罚）：
$$\text{BLEU} = \text{BP}\cdot\exp\left(\sum_{n=1}^{N} w_n \log p_n\right),\qquad \text{BP} = \begin{cases}1 & c > r \\ e^{1-r/c} & c \le r\end{cases}$$

**ROUGE-L**（最长公共子序列 F1）：
$$\text{ROUGE-L} = \frac{(1+\beta^2)R_{\text{lcs}}P_{\text{lcs}}}{\beta^2 R_{\text{lcs}}+P_{\text{lcs}}}$$

### 3. 符号说明表

| 符号 | 含义 | 取值范围 | 备注 |
| :--- | :--- | :--- | :--- |
| TP/FP/FN/TN | 混淆矩阵四格 | 非负整数 | 二分类基础 |
| $P, R, F1$ | 精确率/召回/F1 | $[0,1]$ | F1 是调和平均 |
| $H$ | 平均交叉熵 | $\ge 0$ | PPL 的底数 |
| $p_n$ | n-gram 精确率 | $[0,1]$ | BLEU 用 1-4 gram |
| $c, r$ | 候选/参考长度 | 整数 | BP 长度惩罚 |
| $\beta$ | F 分数权重 | 通常 1 | ROUGE-L 默认 F1 |

### 4. 常见变体与适用条件
- **宏平均 vs 微平均**：多分类下宏平均（每类 F1 平均）对少数类敏感；微平均（全局 TP/FP 汇总）被多数类主导——类别不平衡时报告两者。
- **BLEU 变体**：BLEU-4（N=4，MT 标准）；smoothing（零计数时加平滑避免 log0）。
- **ROUGE 变体**：ROUGE-N（n-gram 召回）、ROUGE-L（LCS）、ROUGE-S（跳二元组）；摘要任务以 ROUGE-1/2/L 为主。
- **适用条件**：PPL 只适合**同词表同 tokenizer** 的模型间比较（跨词表无意义）；BLEU 对短句偏严（BP 惩罚）、对同义改写不敏感；GLUE 适合 10 万级标注数据的标准任务（大模型时代已饱和，转 SuperGLUE/MMLU）。

## 6. 推导思路和思想来源

- **最初困难**：早期 MT 评测靠人工打分（昂贵、不可复现）；分类评测只用 Acc（被不平衡数据欺骗）。
- **直接方法局限**：人工评分不可规模化；Acc 对"稀有正类"失效；逐字匹配对生成任务过严。
- **关键"转念"**：① 分类：把"预测-真实"两两配对（混淆矩阵），P/R/F1 分别回答"准不准/全不全/综合"；② 生成：把"质量"换成"与参考的 n-gram 重叠"（BLEU 来自 IBM 统计 MT 的"机器译文越接近人工译文越好"假设）；③ LM：把"概率"取负对数平均再指数化，得到"等效候选数"（PPL）。
- **推导主线与动机**：任务目标 → 可计算代理量 → 归一化/惩罚项 → 标准化基准（GLUE 把 9 个任务 + 对应指标打包，让模型可比）。
- **为什么自然得到此结论**：每个指标都是"目标 + 工程约束"的折中：F1 调和平均惩罚"偏科"，BLEU 长度惩罚防"刷短句"，PPL 指数化让数值符合直觉——都是为了让分数"讲人话"。

## 7. 例子：基础 → 中等 → 实际应用

### 例子 1：基础例子（可手算）
- **题目**：垃圾邮件分类，测试集 100 封：预测为正且真是正 40（TP），预测正但实际非 10（FP），预测非但实际正 5（FN）。求 Acc、P、R、F1。
- **解题思路与关键步骤**：TN = 100-40-10-5 = 45。Acc = (40+45)/100 = 0.85；P = 40/50 = 0.8；R = 40/45 ≈ 0.889；F1 = 2×0.8×0.889/(0.8+0.889) ≈ 0.842。
- **最终答案**：Acc=0.85，P=0.8，R≈0.889，F1≈0.842。
- **易错点**：F1 是**调和**平均（$2PR/(P+R)$）不是算术平均（$(P+R)/2=0.8445$——本例接近但不同）；FN 漏算导致 R 错误。
- **🤔 追问**：如果垃圾邮件只占 1%（不平衡），Acc 还可靠吗？—— 全猜"非垃圾" Acc=99%，但 R=0；此时必须看 F1（或 PR-AUC）。

### 例子 2：中等例子（条件判断与多步推理）
- **题目**：计算 BLEU-1（仅 unigram）与 BP：候选 "the cat"（c=2），参考 "the cat is on the mat"（r=6）。
- **解题思路与完整解答**：unigram 匹配：the×1（参考中 the 出现 2 次，候选 1 次→计 1）、cat×1 → 匹配数 2，候选总词数 2 → $p_1 = 1.0$。$c=2 \le r=6$ → BP $= e^{1-6/2} = e^{-2} \approx 0.135$。BLEU-1 $= 0.135 \times 1.0 = 0.135$。
- **最终答案**：BLEU-1 ≈ 0.135。含义：候选太短，即使词全对也被长度惩罚压到很低——**BP 惩罚"抄短句"**。
- **易错点**：忘记 BP（短候选 BLEU 会虚高）；count 裁剪（clipping）：候选 "the the" 参考 "the cat" 时 the 只能计 1 次。
- **🤔 追问**：候选改成 "the cat is on the mat"（c=6）？—— $p_1=1$，$c=r$ → BP=1 → BLEU-1=1.0。完全匹配得满分。

### 例子 3：实际应用例子（真实场景/代码）
- **实际价值与转化**：HW04 的 BLEU 验收脚本与 HF `evaluate` 库（HW05 L1 档的 `compute_metrics`）。代码形态：
```python
# 手写 F1（HW02 报告用）
def f1(preds, labels):
    tp = sum(p == 1 and l == 1 for p, l in zip(preds, labels))
    fp = sum(p == 1 and l == 0 for p, l in zip(preds, labels))
    fn = sum(p == 0 and l == 1 for p, l in zip(preds, labels))
    p = tp / (tp + fp) if tp + fp else 0
    r = tp / (tp + fn) if tp + fn else 0
    return 2 * p * r / (p + r) if p + r else 0

# 用 evaluate 库（HW05）
from evaluate import load
bleu = load("bleu")
print(bleu.compute(predictions=["the cat is on the mat"],
                   references=[["the cat is on the mat"]]))   # {'bleu': 1.0}
```

## 8. 常见误区和易混概念

### 误区 1：以为"准确率越高模型越好"
- **错误直觉**：Acc 是万能指标，越高越好。
- **为什么错**：类别不平衡时 Acc 失效（99:1 数据全猜多数类 Acc=99%）；代价不对称时（漏诊 vs 误诊）Acc 不能体现。
- **正确理解**：先看数据分布，再选指标：不平衡/代价敏感用 P/R/F1/PR-AUC；平衡分类用 Acc 也行但建议同时报 F1。

### 误区 2：以为"BLEU 越高翻译一定越好"
- **错误直觉**：BLEU 是翻译质量的完美度量。
- **为什么错**：BLEU 只测 n-gram 词汇重叠：同义改写（"obtained" vs "got"）被罚；句法完全不同的好翻译分数低；对短句严（BP）、对长句松。人工评测仍是金标准。
- **正确理解**：BLEU 是"低成本、可复现"的代理指标，需配合人工抽检与错误分析。

### 概念对比表

| 概念 | 核心问题 | 关键区别 | 典型使用场景 |
| :--- | :--- | :--- | :--- |
| Acc/F1（本概念） | 分类质量 | 混淆矩阵派生 | HW02 分类、SST-2 |
| PPL | LM 不确定性 | 交叉熵指数化 | 语言模型（HW 外） |
| BLEU | 翻译忠实度 | n-gram 精确率+BP | HW04 NMT 验收 |
| ROUGE | 摘要覆盖度 | n-gram/LCS 召回 | 摘要评测 |
| GLUE | 综合理解力 | 9 任务打包 | 预训练模型对比（HW05） |

### 题目与解析

#### 1. 类别分布 95:5 的二分类，全猜多数类的 Acc 是多少？为什么需要换指标？
> [!question]- 答案解析
> - **答案**：Acc=0.95。但模型没有学到任何判别能力（R=0，P 无定义/0），少数类全漏——若少数类是"欺诈/疾病"，代价极高。
> - **解析**：用 F1（或 PR-AUC、召回率@阈值）替代；报告时同时给分布（"95:5"）让读者理解 Acc 背景。
> - **易错原因**：只报 Acc 不报分布。
> - **Obsidian 标签建议**：`#自测题/基础`

#### 2. TP=30，FP=10，FN=20，TN=40，求 P、R、F1、Acc。
> [!question]- 答案解析
> - **答案**：P=30/40=0.75；R=30/50=0.6；F1=2×0.75×0.6/(0.75+0.6)=0.9/1.35≈0.667；Acc=(30+40)/100=0.7。
> - **解析**：F1 低于两者算术平均 0.675 吗？调和平均 0.667 < 0.675——调和平均偏向较小值，惩罚"偏科"（R 拖后腿）。
> - **易错原因**：F1 用错公式（如 $(P+R)/2$）。
> - **Obsidian 标签建议**：`#自测题/基础`

#### 3. 摘要任务该用 BLEU 还是 ROUGE？为什么？
> [!question]- 答案解析
> - **答案**：用 ROUGE（尤其 ROUGE-1/2/L）。摘要的参考摘要只是"内容要点"的一种写法，评测关注**要点是否覆盖**（召回视角）；BLEU 是精确率视角（译文用词是否贴合参考），对摘要的"信息覆盖"不敏感。
> - **解析**：ROUGE-N 计算候选对参考的 n-gram 召回；ROUGE-L 用 LCS 捕获最长匹配片段，对语序更鲁棒。翻译任务才用 BLEU（忠实度优先）。
> - **易错原因**：摘要用 BLEU（分数普遍偏低且与人工相关性差）。
> - **Obsidian 标签建议**：`#自测题/中等`

#### 4. 两个语言模型 A、B 用不同 tokenizer（A 词级、B 子词级），PPL 能直接比吗？
> [!question]- 答案解析
> - **答案**：不能。PPL 依赖 token 划分：子词级 token 多、每个 token 预测更容易（PPL 更低），词级反之；交叉熵的"每 token"平均在不同划分下不可比。
> - **解析**：PPL 只用于**同词表、同 tokenizer、同数据**的模型对比（如消融实验）；跨模型族比较用下游任务指标（GLUE/MMLU）。
> - **易错原因**：拿不同 tokenizer 的 PPL 直接比大小。
> - **Obsidian 标签建议**：`#自测题/中等`

#### 5. 为"新闻摘要"系统设计评测方案（含自动+人工），并说明各环节为什么必要。
> [!question]- 答案解析
> - **答案**：① 自动：ROUGE-1/2/L（内容覆盖）+ BERTScore（语义相似度，对同义改写鲁棒）；② 长度约束检查（摘要长度比例、是否截断）；③ 事实一致性抽检（命名实体是否与原文一致——ROUGE 测不出编造）；④ 人工：双人打分（相关/连贯/事实），不一致时第三人仲裁；⑤ 报告时给出自动-人工相关性（如 Kendall τ）作为可信度佐证。
> - **解析**：自动指标便宜可复现但测不出"幻觉"；人工贵但金标准；两者结合并报告相关性是现代评测规范。
> - **易错原因**：只上 ROUGE 就宣称达标（漏掉事实一致性这一摘要核心风险）。
> - **Obsidian 标签建议**：`#自测题/较难`
