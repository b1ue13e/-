# 🎓 HW06 - 开放课程项目正式作业说明书

> 这是一份老师正式发包用的作业说明书。  
> 它定义题目边界、教学目标、验收口径和交付格式，不提供实验答案。

---

## 一、作业主题

在完成前五份作业后，自主选择一个计算机视觉问题，组织一份完整的小型课程项目交付，包括：

1. `proposal`
2. `milestone`
3. `baseline`
4. `final report`
5. 最小可复核实现或实验链路

这份作业的重点不是“做最大项目”，而是证明学生已经具备独立定义问题、设计 baseline、组织实验和说明边界的能力。

---

## 二、布置时机

这份作业应放在以下内容之后发出：

1. 已完成 `HW01-HW05`；
2. 已具备分类、迁移学习或检测中的至少一种稳定实验经验；
3. 已理解 proposal、milestone 和 final report 的作用；
4. 已能独立组织最小实验协议。

**为什么在这个时点布置：**

- project 不应该是“随便做点东西”的兜底项；
- 只有当前五份作业把协议、对照、分析和工程意识都立住后，开放项目才有教学意义。

---

## 三、前置知识

开始这份作业前，学生至少应具备以下前置：

- 至少一条稳定的视觉任务训练链路；
- baseline 与改进方法公平对照意识；
- 失败样本与边界分析意识；
- 最小工程组织能力；
- 报告写作能力。

如果以下内容仍然不稳，建议先回补：

- 为什么 project 必须先有 baseline，再谈改进；
- 为什么问题定义不清会让整个项目失效；
- 为什么 project 的价值不在于规模，而在于证据质量。

---

## 四、教学目标

完成这份作业后，学生应证明自己具备以下能力：

1. 能独立提出一个合适的视觉问题；
2. 能设计一个可复核的最小实验协议；
3. 能给出合理 baseline，而不是直接上复杂模型；
4. 能按 proposal -> milestone -> final report 推进项目；
5. 能明确项目结论的边界、失败和后续方向。

---

## 五、老师提供什么

老师应提供以下内容，但不替学生完成实验：

- proposal 模板；
- milestone 模板；
- final report 模板；
- 项目评分标准；
- FAQ / submission checklist / milestones / grader notes。

老师不提供：

- 代选题；
- 代设计实验；
- 最终实现；
- 最终结论。

---

## 六、作业任务

### 任务 1：提交 proposal

学生需要明确写清：

- 研究问题是什么；
- 为什么这个问题值得做；
- 数据从哪里来；
- baseline 是什么；
- 成功标准是什么；
- 预期风险是什么。

### 任务 2：提交 milestone

学生需要说明：

- 当前已完成什么；
- 哪些地方卡住了；
- 当前 baseline 是否已经跑通；
- 后续计划是否需要调整。

### 任务 3：完成最小 baseline

学生需要：

- 明确定义 baseline；
- 在固定协议下跑通 baseline；
- 给出最小可复核证据。

### 任务 4：完成改进尝试

学生需要：

- 在 baseline 基础上做一项清楚的改进；
- 说明改进为什么值得；
- 记录改进是否真的有效。

### 任务 5：完成 final report

学生至少需要回答：

- 这个项目究竟解决了什么；
- 它没有解决什么；
- 实验结果是否可靠；
- 后续如果继续做，最值得推进哪一步。

---

## 七、数据与实验协议

这份作业必须遵守以下统一协议：

1. 问题定义必须清楚；
2. baseline 必须先于改进方法；
3. 数据、切分、评价指标必须清楚；
4. 至少保留一个失败点或边界说明；
5. proposal、milestone、final report 三者必须逻辑一致；
6. 所有主要结论都要能从提交物中复核出来。

建议记录但不强制预先追求的内容：

- 成本对比；
- 多随机种子；
- 消融实验；
- 额外可视化分析。

---

## 八、评分标准

总分 `100` 分，建议按以下口径评分：

| 维度 | 分值 | 评分关注点 |
|:---|---:|:---|
| 问题定义与 proposal | 20 | 问题、数据、baseline、成功标准是否清楚 |
| baseline 与实验协议 | 20 | baseline 是否合理且可复核 |
| 改进尝试与对照 | 20 | 是否有清楚改进与公平比较 |
| 分析与边界说明 | 20 | 是否解释失败、限制和下一步 |
| 过程交付与可复现性 | 20 | milestone、README、结果与 final report 是否完整 |

**通过线建议：**

- `75/100` 及以上；
- 且所有硬验收项通过。

---

## 九、硬验收项

以下项目任一失败，都不能靠总分抵消：

- [ ] 已提交 proposal；
- [ ] 已提交 milestone；
- [ ] baseline 已跑通；
- [ ] 至少有一项清楚的改进尝试；
- [ ] final report 可复核；
- [ ] 至少有一个失败点或边界说明；
- [ ] 没有直接照搬外部答案或整仓项目成果。

---

## 十、交付格式

建议统一使用以下目录：

```text
submission/
├── README.md
├── proposal.md
├── milestone.md
├── manifest.yml
├── src/
├── tests/
├── artifacts/
└── report.md
```

### 最低交付要求

#### 1. `README.md`

必须写清：

- 项目要解决什么问题；
- 数据从哪里来；
- 如何运行 baseline；
- 如何运行改进方法；
- 如何复核最终结果。

#### 2. `proposal.md`

至少包含：

- 问题定义；
- 数据与评价协议；
- baseline；
- 风险；
- 计划安排。

#### 3. `milestone.md`

至少包含：

- 已完成工作；
- 当前结果；
- 阻塞点；
- 后续调整。

#### 4. `manifest.yml`

至少记录：

- 数据版本；
- 评价指标；
- baseline；
- 改进方法；
- 随机种子；
- 运行入口；
- 结果文件位置。

#### 5. `src/`

包含：

- baseline 实现；
- 改进实现；
- 训练与评测入口；
- 分析逻辑。

#### 6. `tests/`

至少包含：

- 一个 smoke test；
- 一个最小复核检查。

#### 7. `artifacts/`

建议包含：

- 对照结果表；
- 关键图表；
- 失败案例；
- 日志摘要。

#### 8. `report.md`

至少回答：

1. baseline 是什么，为什么合理；
2. 改进是否真的有效；
3. 项目的边界和失败在哪里；
4. 如果继续做，最值得推进哪一步。

---

## 十一、老师批改时主要看什么

老师最关心的不是“项目做得有多大”，而是：

1. 问题定义是否清楚；
2. baseline 是否成立；
3. 改进是否有证据；
4. 是否真实汇报失败与边界；
5. 提交物能不能让别人复核。

老师明确不以以下内容作为唯一标准：

- 是否选了最热门题目；
- 是否堆了最多模型；
- 是否只展示成功截图。

---

## 十二、与课程主线的关系

这份作业是课程主线中的最终综合闸门。

它不要求学生在短时间内做出研究级成果，但要求学生证明：

- 你已经能像一个初级研究者或工程实践者那样组织问题；
- 你已经能提出 baseline、跑通实验、解释失败；
- 你已经能把一门课里学到的方法整合成一份完整交付。
