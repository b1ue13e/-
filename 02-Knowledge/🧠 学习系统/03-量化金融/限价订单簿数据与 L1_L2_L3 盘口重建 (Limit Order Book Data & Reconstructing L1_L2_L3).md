# 限价订单簿数据与 L1/L2/L3 盘口重建 (Limit Order Book Data & Reconstructing L1/L2/L3)

---

## 0. 先判断它值不值得深挖

**分类：A 类（核心概念，必须深挖）**

**理由：**
限价订单簿（Limit Order Book, LOB）是现代化电子连续竞价交易所（如上交所、深交所、CME、Binance）的“心脏”。所有的资产价格变化本质上全是由 LOB 内部买卖单的撮合与排队引起的。在量化高频交易、做市策略、最优执行与微观结构研究中，深入理解 Level-1（买一卖一快照）、Level-2（多档买卖挂单快照）与 Level-3（逐笔委托与逐笔成交逐笔重建）的底层数据结构，是高频量化架构师与研究员的绝对基本功。

---

## 1. 这个知识点解决什么问题？

> **我们遇到了什么麻烦：**

假设你正在编写一个高频对冲策略。普通的股票行情软件（K 线图）只提供 1 分钟或 1 天的 OHLCV（开高低收成交量）数据。
当你看到 1 分钟阳线时，你无法知道：
- 这 1 分钟内，是买方一口气吃光了盘口？还是卖方撤走了挂单？
- 盘口深处是否有隐藏的隐冰山大单（Iceberg Order）？
- 买卖双方在多大的价格范围内挂了多少防守单？

**以前的方法在哪里卡住：**
1. **Low-freq K线数据失真**：K线消除了所有微观时间戳（Timestamp）与价格跳动路径信息。
2. **缺乏盘口深度维度 (Depth)**：只看历史成交价，无法感知盘口流动性供给（Liquidity Provision）的厚薄。

**为什么必须引入限价订单簿 (LOB) 数据：**
在毫秒甚至微秒级别上，实时维护包含所有未成交限价单（Limit Orders）价格与数量的双向优先队列（Priority Queue）。

**它到底解决了哪类问题：**
解决了**市场微观流动性深度测量、高频盘口买卖失衡感知、以及基于逐笔数据完整重现撮合过程**的问题。

---

## 2. 为什么它重要？它有什么用？

- **体系与大图景**：高频量化与微观结构（第四阶段）的顶层基石，为所有高频因子（OFI, OBI, Micro-price）与最优化算法提供底座。
- **量化与实操应用**：
  1. **L3 逐笔订单簿重建（Order Book Reconstruction）**：利用交易所发出的 Add, Cancel, Execute 逐笔消息，用 C++ 在本地零拷贝（Zero-copy）重构完整的盘口状态。
  2. **高频做市商盘口倾斜 (Inventory Skew)**：根据 L2 买三卖三深度动态计算 Micro-price（微观中枢价）。
  3. **算法交易冲击成本预测**：计算吃掉 $N$ 股所需的深度加权平均价格（WAP）。

---

## 3. 学它之前需要哪些前置知识？

1. **[[订单类型与成交机制]]**：理解限价单（Limit Order）、市价单（Market Order）、取消单（Cancel Order）与“价格优先、时间优先”撮合规则。
2. **最小必要背景（L1/L2/L3 区别）**：
   > - **L1 (Level 1)**：最粗粒度，仅包含最高买价 (Bid1)、最低卖价 (Ask1) 及各自数量（如 3 秒一次）。
   > - **L2 (Level 2)**：十档或五档买卖价格与挂单量快照（如深交所 3 秒/上交所 3 秒发一次）。
   > - **L3 (Level 3 / Order-by-Order)**：最高精细度，包含每一笔原始委托（Order ID, Price, Vol）和逐笔成交，可完美重建任意微秒状态。

## 4. 用直觉语言解释它

### 生活类比：火车站售票处的排队窗口

想象一个繁忙的火车站售票处：
- **买方队列（Bids）**：一群想买票的人，出价最高的人排在队首（买一）。
- **卖方队列（Asks）**：一排想卖票的人，要价最低的人排在队首（卖一）。
- **中间价（Mid-price）**：队首买方和队首卖方之间的价格空隙。
- **L2 快照** 就像：摄像机每 3 秒拍一张照片，记录前 10 个窗口排队的人数。
- **L3 逐笔数据** 就像：门口安检仪，记录“张三在 09:30:00.123 进了第 3 窗口”、“李四在 09:30:00.125 退出了队伍”。

**订单簿数据的直觉本质**：
订单簿就是买卖双方在各个价格阵地上布置兵力（挂单量）与撤退/冲锋（撤单/成交）的实时双向阵地图。

«“订单簿数据就是交易所实时公布的买卖双方向各个价格档位挂单排队的兵力布防图。”»

## 5. 正式定义、核心公式、符号解释

### 核心定义
**限价订单簿 (LOB)**：由电子交易所维护的、包含所有未成交买入与卖出限价单的双向双序列数据结构。买单按“价格从高到低、同价时间从早到晚”排列；卖单按“价格从低到高、同价时间从早到晚”排列。

### 核心计算公式

#### 1. 中中间价 (Mid-price) 与 微观中枢价 (Micro-price)
$$P_{mid} = \frac{P_{ask1} + P_{bid1}}{2}$$
$$P_{micro} = \frac{v_{bid1} \cdot P_{ask1} + v_{ask1} \cdot P_{bid1}}{v_{bid1} + v_{ask1}}$$

#### 2. 静态盘口不平衡比率 (Order Book Imbalance, OBI)
$$OBI_{L1} = \frac{v_{bid1} - v_{ask1}}{v_{bid1} + v_{ask1}} \in [-1, 1]$$

#### 3. $K$ 档深度加权出价 (Depth Weighted Mid-price)
$$P_{depth\_mid} = \frac{\sum_{k=1}^K w_k P_{bid,k} + \sum_{k=1}^K w_k P_{ask,k}}{2 \sum_{k=1}^K w_k}$$

### 符号解释表

| 符号 | 含义 | 维度/量纲 | 备注 |
| :--- | :--- | :--- | :--- |
| $P_{bid,k}, v_{bid,k}$ | 买第 $k$ 档的价格与挂单量 | 价格 / 股数 | $P_{bid,1} > P_{bid,2} > \dots$ |
| $P_{ask,k}, v_{ask,k}$ | 卖第 $k$ 档的价格与挂单量 | 价格 / 股数 | $P_{ask,1} < P_{ask,2} < \dots$ |
| $P_{micro}$ | 考虑盘口挂单厚度的微观中枢价 | 货币单位 | 比普通 Mid-price 更有预测力 |
| $OBI$ | 静态盘口挂单不平衡度 | 无量纲 $[-1, 1]$ | $OBI > 0$ 代表买盘更厚 |
| $w_k$ | 盘口第 $k$ 档的权重 | 标量 | 常用倒数权重 $w_k = 1/k$ |

## 6. 推导思路和思想来源

### 为何 Micro-price 比简单 Mid-price 更有预测力？
1. **简单 Mid-price 的缺陷**：若 $Bid1 = 10.00$（挂单 10,000 手），$Ask1 = 10.02$（挂单仅 10 手）。
   普通 Mid-price 简单算术平均为 $10.01$ 元。但由于买盘极其浑厚、卖盘极薄，下一个市价买单只要 10 手就会瞬间把卖一吃光，推动中间价格跳涨！
2. **转念（概率加权）**：
   中间价跳升至 10.02 的概率远高于跳降至 10.00。将挂单量反向加权：
   $$P_{micro} = \frac{10000 \times 10.02 + 10 \times 10.00}{10000 + 10} \approx 10.01998 \text{ 元}$$
   Micro-price 极度偏向 10.02 元，提前预测了盘口的向上跳动！

## 7. 例子：基础 → 中等 → 实际应用

### 例子 1：基础手算例题（Micro-price 与 OBI 计算）

**题目**：
某股票 L2 盘口买一卖一快照如下：
- $P_{bid1} = 20.00$ 元，$v_{bid1} = 800$ 手
- $P_{ask1} = 20.10$ 元，$v_{ask1} = 200$ 手

求此时的普通 Mid-price、Micro-price 以及 $OBI_{L1}$。

**解答过程**：
1. 普通 Mid-price：
   $$P_{mid} = \frac{20.00 + 20.10}{2} = 20.05 \text{ 元}$$
2. Micro-price 计算：
   $$P_{micro} = \frac{800 \times 20.10 + 200 \times 20.00}{800 + 200} = \frac{16080 + 4000}{1000} = \frac{20080}{1000} = 20.08 \text{ 元}$$
3. $OBI_{L1}$ 计算：
   $$OBI_{L1} = \frac{800 - 200}{800 + 200} = \frac{600}{1000} = +0.60$$
4. **结论**：$P_{micro} (20.08) > P_{mid} (20.05)$ 且 $OBI = +0.60$，代表买方挂单极其厚实，价格大概率向上微调。

### 例子 2：中等例题（L3 逐笔事件对订单簿状态的更新）

**题目**：
初始盘口买一为 10.00 元（挂单量 500 手，包含订单 A 300 手和订单 B 200 手）。
接着发生连续 3 个 L3 逐笔事件：
1. `Event 1`: 撤单指令 (Cancel)，取消订单 A 中 100 手。
2. `Event 2`: 新限价单 (Add)，在 10.00 元挂入订单 C 400 手。
3. `Event 3`: 主动卖出市价单成交 (Execute)，成交 500 手。

计算 Event 3 完成后，买一 10.00 元处的剩余挂单量。

**解答过程**：
1. 初始买一挂单量：$500$ 手（A:300, B:200）。
2. `Event 1` 撤单后：买一剩余 $500 - 100 = 400$ 手（A:200, B:200）。
3. `Event 2` 加单后：买一增加 $400$ 手，总量变为 $400 + 400 = 800$ 手（A:200, B:200, C:400）。
4. `Event 3` 成交 500 手：根据“时间优先”原则，首先吃光 A 的 200 手和 B 的 200 手，再吃掉 C 的 100 手。
5. 最终买一 10.00 元处剩余挂单量：$800 - 500 = 300$ 手（全为订单 C 剩余）。

### 例子 3：实际应用（Python 重建多档盘口深度与展示）

```python
import numpy as np
import pandas as pd

# 构造一个 5 档 L2 订单簿快照数据结构
order_book_l2 = {
    'bids': [(10.00, 500), (9.99, 1200), (9.98, 800), (9.97, 2000), (9.96, 1500)],
    'asks': [(10.01, 300), (10.02, 600), (10.03, 1000), (10.04, 1500), (10.05, 3000)]
}

# 计算 5 档累计挂单深度
df_bids = pd.DataFrame(order_book_l2['bids'], columns=['price', 'vol'])
df_asks = pd.DataFrame(order_book_l2['asks'], columns=['price', 'vol'])

total_bid_depth = df_bids['vol'].sum()
total_ask_depth = df_asks['vol'].sum()

print(f"买方 5 档总挂单深度: {total_bid_depth} 手")
print(f"卖方 5 档总挂单深度: {total_ask_depth} 手")
print(f"五档深度不平衡度 OBI_5: {(total_bid_depth - total_ask_depth) / (total_bid_depth + total_ask_depth):.4f}")
```

## 8. 常见误区与易混概念

### 误区 1：只要看懂了 L2 盘口的买一卖一，就不需要看 L3 逐笔数据

错误直觉：“L2 已经包含 10 档买卖价和量了，3 秒一个快照足够做高频了。”  
为什么错：在 3 秒的 L2 快照间隔内，高频机器可能已经发生了 500 笔 Add/Cancel/Execute 交互。只看 3 秒快照会丢掉所有毫秒级别的真实信息，且无法识别“虚假挂单撤单”。  
正确理解：**L2 是离散快照，L3 是连续事件流。高频对冲与做市必须依赖 L3 逐笔重建。**

### 概念对比：L1 vs L2 vs L3 订单簿数据

| 维度 | Level-1 (L1) | Level-2 (L2) | Level-3 (L3 / Tick-by-Tick) |
| :--- | :--- | :--- | :--- |
| **精细度** | 仅买一/卖一快照 | 5 档或 10 档买卖快照 | 逐笔委托、逐笔成交与全撤单明细 |
| **时间推送频次** | 慢 (1 秒 ~ 3 秒) | 中 (500 毫秒 ~ 3 秒) | **极快 (微秒级事件驱动推送)** |
| **数据量与处理要求** | 极低（Python 轻松处理） | 中等 | 极高（需 C++ 零拷贝内存解析） |
| **应用场景** | 散户交易、日内中低频策略 | 量化算法拆单 (VWAP/TWAP) | **高频做市、HFT 套利、微观结构研究** |

### 第 4 题：变式/综合（中等）
**题目**：什么是“冰山订单 (Iceberg Order)”？在 L2 订单簿快照中，冰山订单会展现出什么特征？

> [!question]- 答案解析
> **答案**：
> 1. **定义**：机构为了隐蔽大单意图，只在盘口暴露一小部分挂单（如 100 手），当这 100 手成交后，系统自动从隐藏库中补充 100 手。
> 2. **L2 特征**：某个价格档位的挂单不断被吃掉，但该档位的挂单数量却反复“凭空刷新复活”，价格长时间无法被吃穿。

### 第 5 题：开放/建模（较难）
**题目**：在设计高频交易系统的订单簿模块时，为什么不能使用 Python 字典或 std::map 来存储盘口订单？推荐使用什么数据结构？

> [!question]- 答案解析
> **解析**：
> 1. **局限**：`std::map` 基于红黑树，插入和查找涉及频繁的动态内存分配（`malloc`）与指针解引用，易引发 CPU Cache Miss，延迟高达数百纳秒。
> 2. **推荐结构**：
>    - 价格档位：使用连续内存的**静态数组 (Flat Array)**，以 Price 偏移量作为 Index 直接寻址，查找 $O(1)$。
>    - 同价队列：使用**预分配的环形队列 (Ring Buffer)** 或静态双向链表，避免任何运行时内存分配。  
> **Obsidian 标签**：`#自测题/高频数据结构`
