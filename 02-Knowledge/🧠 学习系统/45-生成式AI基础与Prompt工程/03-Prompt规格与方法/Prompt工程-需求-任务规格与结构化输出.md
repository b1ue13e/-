# Prompt 工程：任务规格与结构化输出

## 0. 学习边界

- **类别**：**A 类（核心概念，必须深挖）**。
- **判断理由**：模型版本会变化，所谓“魔法措辞”会失效；任务目标、输入边界和验收条件才是可迁移资产。

## 1. 这个知识点解决什么问题？

> “帮我总结一下”没有说明面向谁、保留什么、禁止什么、输出多长，也没有定义何为合格。模型只能猜，失败后用户又无法定位是哪条要求缺失。

## 2. 为什么它重要？它有什么用？

- **连接大图景**：规格是评测集、Guardrail、结构化输出和 Agent 工具参数的共同起点。
- **实际场景**：报告摘要、信息抽取、客服答复、代码生成和批处理。
- **高频任务**：把自然语言目标改成可检查的输入/输出契约。

## 3. 学它之前需要哪些前置知识？

1. **[[生成式AI-基础-概率生成Token与能力边界]]**：理解模型不会自动知道隐含要求。
2. **JSON 基础**：对象、数组、字符串、数字和布尔值。

## 4. 用直觉语言解释它

> “写 Prompt 像给外包团队写验收合同，而不是给演员一句角色台词。”

- 先写**目标**，再写**输入事实**。
- 把**规则**分成必须、禁止和异常处理。
- 给出**输出 Schema**，最后写**验收样例**。
- 一句话本质：Prompt 的核心是完整、无冲突、可验证的任务规格。

## 5. 正式定义、核心公式、符号解释

### 1. 最核心定义

一个可评测 Prompt 规格可表示为：

$$S=(G,I,C,R,O,F,E),$$

分别代表目标 Goal、输入 Input、上下文 Context、规则 Rules、输出 Output、失败处理 Failure、例子 Examples。

### 2. 核心公式

规格覆盖率：

$$Coverage=\frac{\text{测试集中可由明确规则判定的要求数}}{\text{全部重要要求数}}.$$

### 3. 符号说明表

| 符号 | 含义 | 示例 |
| :--- | :--- | :--- |
| $G$ | 用户最终目标 | 提取合同风险 |
| $R$ | 约束与业务规则 | 不推断未出现日期 |
| $O$ | 输出契约 | 固定 JSON 字段 |
| $F$ | 信息不足处理 | `status=insufficient` |

### 4. 常见变体与适用条件

- 开放创作允许宽输出；批处理和工具调用应使用强 Schema。
- 系统规则、开发规则、用户输入和外部文档必须分区，避免数据伪装成指令。
- “语气像专家”不能替代领域规则和验收标准。

## 6. 推导思路和思想来源

- **最初困难**：Prompt 优化常退化成无目的改词。
- **关键转念**：先把失败样本转成缺失要求，再修改规格。
- **主线**：收集真实任务 → 写成功/失败样例 → 提取要求 → 排优先级 → 定义 Schema → 建测试集 → 迭代。

## 7. 例子：基础 → 中等 → 实际应用

### 例子 1：基础例子（可手算）

某摘要任务有 5 条重要要求，只明确写了受众、长度和格式 3 条，覆盖率为 $3/5=60\%$。漏掉“保留数字”和“资料不足不得补写”，这两类错误不会靠调整语气解决。

### 例子 2：中等例子

把“分析工单”改成：目标=分类并给优先级；输入=工单正文；规则=只用给定文本、无证据时 `unknown`；输出=`category/priority/evidence`；失败=缺正文返回 `invalid_input`。

### 例子 3：实际应用例子（可运行 Python）

```python
# 输入：模型返回的 JSON 字符串；输出：校验后的对象或明确错误。
import json

raw = '{"category":"billing","priority":2,"evidence":"重复扣款"}'
data = json.loads(raw)
required = {"category": str, "priority": int, "evidence": str}
errors = [key for key, kind in required.items()
          if key not in data or not isinstance(data[key], kind)]
if errors:
    raise ValueError(f"schema_error: {errors}")
print(data)
# 预期：打印通过类型检查的三个字段。
```

## 8. 常见误区和易混概念

### 误区 1：Prompt 越长越好
- **为什么错**：重复、冲突和无关要求会增加歧义。
- **正确理解**：只保留能改变输出或验收的要求。

### 误区 2：JSON 提示等于 JSON 保证
- **为什么错**：提示只是概率约束，生产系统仍需解析、校验和重试。

### 概念对比表

| 概念 | 核心问题 | 关键区别 | 场景 |
| :--- | :--- | :--- | :--- |
| Persona | 用什么表达风格 | 软约束 | 创作/解释 |
| 任务规格 | 做什么才算合格 | 业务真值 | 所有重复任务 |
| Schema | 输出能否机器消费 | 结构约束 | API/批处理 |

## 11. 自测题：5 道

1. “你是一位专家”属于哪类信息？
   > [!question]- 答案解析 `#自测题/基础`
   > Persona/表达风格，不是业务事实或验收规则。
2. 缺少输入时应该让模型猜吗？
   > [!question]- 答案解析 `#自测题/基础`
   > 不应；规格应定义澄清或 `invalid_input/insufficient`。
3. 为什么规则要可由测试样本触发？
   > [!question]- 答案解析 `#自测题/中等`
   > 没有触发样本就无法知道规则是否真的改变行为。
4. “输出 JSON”为什么仍需校验？
   > [!question]- 答案解析 `#自测题/中等`
   > 模型可能漏字段、错类型、输出额外文本或生成无效 JSON。
5. 为课程推荐任务写 5 条验收要求。
   > [!question]- 答案解析 `#自测题/较难`
   > 至少覆盖目标用户、先修、时间预算、来源可追溯、缺失信息处理；答案应能转为测试样本。
