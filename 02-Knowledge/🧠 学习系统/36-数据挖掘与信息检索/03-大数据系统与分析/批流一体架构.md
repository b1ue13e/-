## 💡 直觉与动机

早期大数据系统采用 **Lambda 架构**（Nathan Marz 提出）：**批处理层**（Hadoop/Spark）负责准确性，**速度层**（Storm/Flink）负责实时性，两条链路并行运行，**Serving 层**合并结果。问题在于：**同一业务逻辑要维护两套代码**（批和流），极高的工程成本和数据一致性风险。

批流一体（Unified Batch & Streaming）的核心思想：**流是批的特例**（有界流 = 批处理；无界流 = 连续批处理），用统一的编程模型和执行引擎消除双路维护成本。

## 📐 正式定义与架构对比

### Lambda 架构（传统）

```
原始数据
    │
    ├──▶ [批处理层 Batch Layer]  ──▶ Batch Views (T+1 准确)
    │         (Hadoop / Spark)
    │
    ├──▶ [速度层 Speed Layer]    ──▶ Realtime Views (近实时，可能有误)
    │         (Storm / Flink)
    │
    └──▶ [服务层 Serving Layer]  ──▶ 合并两路结果响应查询
              (Druid / Hbase)

问题：两套代码 → 维护成本 × 2，数据口径不一致风险
```

### Kappa 架构（简化）

```
所有数据 ──▶ [消息队列] ──▶ [流处理引擎（Flink）] ──▶ 服务层
                (Kafka)      统一处理批和流

优势：一套代码；劣势：历史数据重放性能不如 Spark 批处理
```

### Flink 的有界流 = 批处理统一模型

在 Flink 1.12+ 中，批处理和流处理共用同一套 DataStream/Table API：

$$\text{有界流（Bounded Stream）} \xleftrightarrow{\text{统一 API}} \text{无界流（Unbounded Stream）}$$

执行模式（`RuntimeExecutionMode`）：
- `STREAMING`：逐事件处理，低延迟（实时场景）
- `BATCH`：排序优化，高吞吐（历史数据场景）
- `AUTOMATIC`：根据输入是否有界自动选择

### 实时数仓分层（典型 ODS→DWD→DWS→ADS）

```
ODS（贴源层）→ DWD（明细层）→ DWS（汇总层）→ ADS（应用层）
  Kafka         Flink ETL     Flink 聚合      ClickHouse/Redis
  原始事件        清洗+规范       按维度聚合         业务报表
```

## 💻 最小 Python 实现 — 模拟批流统一处理

```python
from abc import ABC, abstractmethod
from typing import Iterable, Iterator
from datetime import datetime

class DataSource(ABC):
    """统一的数据源抽象（批或流）"""
    @abstractmethod
    def read(self) -> Iterator[dict]:
        pass

class BatchSource(DataSource):
    """有界批处理源（历史数据）"""
    def __init__(self, records: list[dict]):
        self.records = records

    def read(self) -> Iterator[dict]:
        yield from self.records

class StreamSource(DataSource):
    """无界流处理源（模拟实时数据）"""
    def __init__(self, generator: Iterable[dict]):
        self.generator = generator

    def read(self) -> Iterator[dict]:
        yield from self.generator

def unified_word_count(source: DataSource) -> dict:
    """无论批还是流，用同一套逻辑处理词频统计"""
    counts = {}
    for record in source.read():
        for word in record['text'].split():
            counts[word] = counts.get(word, 0) + 1
    return counts

# 批处理模式：处理历史日志
historical_logs = [
    {"text": "data mining retrieval", "ts": "2024-01-01"},
    {"text": "big data spark flink", "ts": "2024-01-02"},
    {"text": "data retrieval search", "ts": "2024-01-03"},
]
batch_result = unified_word_count(BatchSource(historical_logs))
print("批处理词频:", dict(sorted(batch_result.items(), key=lambda x: -x[1])[:5]))

# 流处理模式：模拟实时事件（复用相同函数）
def simulate_stream():
    import time
    events = [{"text": "realtime data processing", "ts": str(datetime.now())}]
    yield from events  # 实际场景中是无限 generator

stream_result = unified_word_count(StreamSource(simulate_stream()))
print("流处理词频:", stream_result)
```

## ⚠️ 常见误区与避坑指南

1. **Lambda 架构的"批处理纠正流"逻辑很复杂**：速度层产生的结果最终要被批处理层覆盖，Serving 层的合并逻辑随业务增长变得极难维护。不要轻易引入 Lambda，优先评估 Kappa 是否满足需求。

2. **Kappa 架构的历史重放代价**：Kappa 用 Kafka 保存历史数据（保留时间有限），历史全量回放（如修 bug 后重算3年数据）需要把全量数据重新灌入 Kafka，延迟高且成本大。Lambda 在这点上仍有优势。

3. **Delta Lake/Iceberg 的 Time Travel 被误解为流处理**：这是版本快照（MVCC），不是流处理。Delta Lake 提供的是"某时间点的数据快照"能力，不等于低延迟实时处理。

4. **ODS 层直接落地到数仓（不做去重）**：Kafka 的消息可能 at-least-once，ODS 层需要用主键去重（Flink Upsert Kafka Connector 或 Delta Lake MERGE INTO）确保幂等。

5. **流处理窗口和批处理时间范围不对齐**：如流处理按1小时滚动窗口，批处理按自然日汇总，在每日边界前后的数据会出现口径不一致（跨窗口的数据重复计算）。需要统一时间切分策略。
