# 倒排索引与布尔检索

---

## 0. 学习边界

- **类别**：**A 类（核心概念，必须深挖）**
- **判断理由**：整条检索链（BM25 → 稠密 → 混合 → 评测）都建立在"文档如何被组织成可查询结构"上；HW02 强制手写索引与布尔合并，HW03 的 BM25、HW04 的向量索引都复用这里的位置信息与 DocVectors。跳过它等于跳过整个信息检索的地基。
---

## 1. 这个知识点解决什么问题？

> **我们遇到了什么麻烦**：
> 我们要在海量文档（百万到十亿级）中回答"哪些文档包含词项 $t$""哪些同时包含 $t_1,t_2$"。直接**顺序扫描**每来一个查询就重读全部文档，复杂度 $O(N)$，在 10 亿文档上完全不可行。以前的方法卡在"查询速度与语料规模成正比"上。
> 因此必须引入**倒排索引**：预先为每个词项建一张"它出现在哪些文档"的名单（倒排表），查询时沿词项直接定位，把 $O(N)$ 扫描变成 $O(\text{结果规模})$ 查找；再加**布尔查询处理**把这些名单做集合合并，支持 AND/OR/NOT 与短语查询。
---

## 2. 为什么它重要？它有什么用？

- **连接大图景**：HW02 的索引与合并是 HW03 BM25（见 [[BM25与TF-IDF]]）的数据来源；HW04 稠密检索（见 [[稠密检索与评估指标]]）同样要建"向量倒排"（IVF 聚类）才能免于全量扫描——"用索引换时间"贯穿整门课。
- **实际应用场景**：Elasticsearch / Lucene 的底层核心；任何搜索引擎的"检索"二字都指这一步；面试高频题"倒排索引如何支持短语查询""跳跃表如何加速合并"。
- **高频题型/任务**：词项-文档矩阵 ↔ 倒排表互转；布尔查询求交/求并；带位置信息的短语查询；跳跃表合并复杂度分析。
---

## 3. 学它之前需要哪些前置知识？

1. **[[哈希表HashTable]]**：倒排词典按词项 $O(1)$ 定位；冲突处理决定索引构建速度。
2. **排序与归并**：建索引标准做法是先按 (词项, docID) 排序再归并；两路归并思想直接复用到倒排表合并。
---

## 4. 用直觉语言解释它

> «"倒排索引就像书末的术语索引"：从正文开头找"倒排"很慢，索引页直接告诉你它在第 45、120、233 页。倒排表就是每个词后面挂的那串页码（文档 ID）；布尔查询就是同时翻几个词的页码列表，把相同页码挑出来。"»

- **直觉类比/几何图像**：词项-文档矩阵是"行=词项、列=文档"的稀疏矩阵；倒排表就是按行压缩（只存非零元）。矩阵太稀疏（一词只在极少文档出现），按行存储天然支持"查词项得文档"。
- **一句话直觉本质**：**把"文档 → 词"预计算成"词 → 文档列表"，用空间换查询时间，再用有序列表合并回答布尔查询。**
---

## 5. 正式定义、核心公式、符号解释

### 1. 最核心定义
- **词项-文档矩阵**：$M \in \{0,1\}^{|V| \times N}$，$M_{t,d}=1$ 表示词项 $t$ 出现在文档 $d$；$V$ 为词表，$N$ 为文档总数。
- **倒排索引**：对每个词项 $t$ 维护**倒排表** $P_t = [d_1, \dots, d_{f_t}]$（$f_t$ = 文档频率），表项为 (docID, 词频, 位置列表)。
- **布尔查询**：查询解析为词项 AND/OR/NOT 表达式，对倒排表做集合运算。

### 2. 核心公式
$$P_{t_1} \cap P_{t_2} = \{d : d \in P_{t_1} \wedge d \in P_{t_2}\},\qquad \text{双指针代价 } O(|P_{t_1}| + |P_{t_2}|)$$
$$\text{跳跃表步长 } \text{skip} = \lfloor \sqrt{L} \rfloor \quad (L = \text{倒排表长度})$$

### 3. 符号说明表

| 符号 | 含义 | 取值范围 / 量纲 | 备注 |
| :--- | :--- | :--- | :--- |
| $V$ | 词表 | $\approx 10^5\text{–}10^6$ | 分词 + 停用词/词干化后 |
| $N$ | 文档总数 | $10^5\text{–}10^9$ | 语料规模 |
| $P_t$ | 词项 $t$ 的倒排表 | 长度 $f_t$ | 按 docID 升序 |
| $f_t$ | 文档频率（df） | $1 \le f_t \le N$ | 与 IDF 相关，见 [[BM25与TF-IDF]] |

### 4. 常见变体与适用条件
- **变体**：文档级倒排（只存 docID）→ 布尔够用；**位置级倒排**表项再存位置列表 → 短语查询；词典放内存、倒排表放磁盘。
- **适用/限制**：查询是词项集合/布尔表达式，语料静态或低更新频率；纯布尔模型**无排序**，NOT 查询需 $N$ 做差集，代价高。
---

## 6. 推导思路和思想来源

- **最初困难**：顺序扫描 $O(N)$ 无法支撑大规模检索，朴素反向映射也无存储优化。
- **关键"转念"**：把查询所需操作**前移到建索引阶段**——查询永远只问"哪个词出现在哪些文档"，就提前存好答案，以预计算换查询延迟。
- **推导主线与动机**：词项-文档矩阵（概念）→ 按行压缩为倒排表（存储）→ 表内按 docID 排序（合并可用双指针线性完成）→ 加位置信息（短语查询）→ 加跳跃指针（常数剪枝）。每一步都由"查询需求"倒推"存储结构"。
- **为什么自然得到此结论**：两个有序表求交的双指针 $O(|A|+|B|)$ 是最优线性解；跳跃表是"比较昂贵"场景下的常数优化。
---

## 7. 例子：基础 → 中等 → 实际应用

### 例子 1：基础例子（可手算）
- **题目**：$d_1$="new york times"，$d_2$="new york post"，$d_3$="los angeles times"，写词项-文档矩阵与倒排表。
- **解题思路与关键步骤**：分词得词表 {"new","york","times","post","los","angeles"}；对每个词项列出出现它的文档（docID 升序）。
- **最终答案**：$6\times3$ 稀疏矩阵；倒排表：`new→[1,2]`，`york→[1,2]`，`times→[1,3]`，`post→[2]`，`los→[3]`，`angeles→[3]`。
- **易错点**：忘记按 docID 升序排序——合并算法依赖有序性。
- **🤔 追问**：若 $d_1$ 中 "new" 出现两次？——表项升级为 (docID, 词频) 如 `new→[(1,2),(2,1)]`，词频正是 BM25 的 $tf$ 输入。

### 例子 2：中等例子（条件判断与多步推理）
- **题目**：查询 `times AND post`，双指针合并 $P_{times}=[1,3]$ 与 $P_{post}=[2]$；若两表都很长（各 1000 项）如何加速？
- **解题思路与完整解答**：指针 $i,j$ 从 0 起：1<2 则 $i{+}{+}$，3>2 则 $j{+}{+}$，$j$ 越界 → 交集为空。**关键推理**：$O(|A|+|B|)$ 已最优，但若比较昂贵（磁盘），可在长表上放跳跃指针（每 $\lfloor\sqrt{L}\rfloor$ 项一个），当 $A_i < B_j$ 且 $B_j$ 超过 $A$ 下一跳时直接跳过。
- **易错点**：跳跃只能在**有序**表上用；跳过头会漏结果——必须保证"跳过区间的最大值仍小于对方当前值"。

### 例子 3：实际应用例子（真实场景/代码）
- **实际价值与转化**：HW02 要求手写倒排索引后与 Pyserini 对拍；`--storePositions --storeDocvectors` 正是为短语查询（位置）与 BM25（DocVectors）提供数据。真实 Lucene 的 BooleanQuery 同样走倒排表合并。
- 代码形态（手写索引 + Pyserini 对照）：
```python
from collections import defaultdict
def build_index(docs):                       # 手写位置级倒排
    index = defaultdict(list)
    for doc_id, text in docs.items():
        for pos, term in enumerate(text.split()):
            index[term].append((doc_id, pos))
    return {t: sorted(v) for t, v in index.items()}

def intersect(p1, p2):                       # AND 合并（双指针）
    i = j = 0; res = []
    while i < len(p1) and j < len(p2):
        if p1[i] == p2[j]: res.append(p1[i]); i += 1; j += 1
        elif p1[i] < p2[j]: i += 1
        else: j += 1
    return res
```
```bash
# Pyserini 对照：建索引（含位置信息）后查询
python -m pyserini.index.lucene --collection JsonCollection --input ./docs \
  --index ./index --generator DefaultLuceneDocumentGenerator --threads 8 \
  --storePositions --storeDocvectors
python -m pyserini.search.lucene --index ./index --topics queries.json --output run.txt
```

## 8. 常见误区和易混概念

### 误区 1：倒排索引就是"反向的文档"
- **错误直觉**：倒排 = 把每篇文档的词倒着存；**为什么错**："倒排"指"词项 → 文档列表"的映射方向与"文档 → 词项"相反，与拼写方向无关。
- **正确理解**：正向索引按文档存词，倒排索引按词存文档列表，是同一矩阵的两种压缩方向。

### 误区 2：布尔检索和 BM25 检索是一回事
- **错误直觉**：都是"输入查询词、输出文档"，只是打分函数不同；**为什么错**：布尔模型输出**无序命中集合**（无排序），BM25（见 [[BM25与TF-IDF]]）输出**带分数排序列表**，还需词频与文档长度。
- **正确理解**：布尔做"筛选"（过滤层），BM25 做"排名"（排序层），现代系统两者叠加。

### 概念对比表

| 概念 | 核心问题 | 关键区别 | 典型使用场景 |
| :--- | :--- | :--- | :--- |
| 正向索引 | 文档里有哪些词 | 按文档组织 | DocVectors 存储 |
| 倒排索引 | 词出现在哪些文档 | 按词项组织 | 查询处理 |
| 布尔模型 | 是否命中 | 无排序、集合运算 | 过滤、专业检索语法 |
| 向量空间模型 | 相关程度排序 | 余弦相似度打分 | 见 [[BM25与TF-IDF]] |

### 题目与解析

#### 1. 正向索引与倒排索引的核心区别是什么？
> [!question]- 答案解析
> - **答案**：正向索引按"文档 → 词项"组织，倒排索引按"词项 → 文档列表"组织；倒排索引把"某词出现在哪些文档"从 $O(N)$ 扫描降为 $O(1)$ 定位。
> - **解析**：二者是同一词项-文档矩阵的不同压缩方向；倒排表按 docID 有序存储以便线性合并。
> - **易错原因**：把"倒排"误理解为"逆序存储"。
> - **对应误区**：误区 1。
> - **Obsidian 标签建议**：`#自测题/基础`

#### 2. 文档集 $d_1$="cat dog"，$d_2$="dog bird"，$d_3$="cat bird bird"，写出每个词项的倒排表与文档频率 $f_t$。
> [!question]- 答案解析
> - **答案**：`cat→[1,3]`，`dog→[1,2]`，`bird→[2,3]`，$f_t$ 均为 2。
> - **解析**：每词项收集出现它的 docID 升序排列；$f_t$ = 列表长度。`bird` 在 $d_3$ 出现两次不改变 $f_t$，但词频（tf）记为 2。
> - **易错原因**：把"词频 tf"（篇内次数）与"文档频率 df"（篇数）混淆。

#### 3. 什么条件下给倒排表加跳跃指针才划算？
> [!question]- 答案解析
> - **答案**：倒排表很长、且比较（含磁盘读取）比指针移动昂贵时划算；步长 $\lfloor\sqrt{L}\rfloor$；短表上跳跃反而增加开销。跳跃表目标是减少与"不可能命中的项"的比较次数。
> - **易错原因**：认为跳跃表总是更快；且跳跃只对有序表有效，跳过头会漏结果。

#### 4. 如何支持短语查询 "new york"（词序相邻）？需要倒排表存什么？
> [!question]- 答案解析
> - **答案**：需要**位置级倒排**：表项存 (docID, 位置列表)；对 `new` 与 `york` 的位置列表做"位置差 = 1"的合并（$pos_{york}=pos_{new}+1$）。
> - **解析**：只有 docID 无法判断词序与相邻性；位置列表让短语查询变成两个有序位置表的滑动合并。
> - **易错原因**：用"同时出现"代替"相邻出现"——"new times york" 会假命中 "new york"。

#### 5. 证明双指针 AND 合并复杂度为 $O(|A|+|B|)$，并说明 NOT 查询为什么更贵。
> [!question]- 答案解析
> - **答案**：每个指针只前进、每次循环至少移动一个指针，总步数 ≤ $|A|+|B|$，线性最优；NOT 查询需扫描 $B$ 或用 $N$ 做差集，无法对称剪枝。
> - **解析**：这是 HW02 合并算法正确性的理论依据；NOT 代价的根源是"补集没有倒排表"。
> - **易错原因**：认为 NOT 和 AND 一样便宜；实际常转换为"排除已检索结果"的后过滤。
